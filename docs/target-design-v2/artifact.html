Chapter 0导读与基线

这份文档回答一个问题：如果从原理出发重新设计这个仿真器的模型表示，应该长什么样。 它不是对现有代码的改造清单，而是目标形态的分层规范——每一层讲四件事：是什么、 为什么这样切、主要数据结构、数据流与逻辑流程。

要解决的四个问题

问题今天的形态本方案
模型演进速度 op 图与 saves=[...] 手写在 Python 里，框架代码一改就烂且静默失效 结构从源码抽取，重跑编译即更新
未知算子 三种不一致结果：抛错 / 只进 opaque_calls / 透传首输入 shape 统一阻断 + 生成待填骨架
两条链各自为政 显存吃手写图、时间吃抽取图；轴代入、反向语义各实现一遍 共享 Structure + Backward + Placement，后端只剩口径壳
不确定性无处安放 时间侧有退化阶梯与 confidence；形状/内存侧只有「精确或阻断」 provenance 作为全 IR 横切契约（第 2 章）
为什么值得重做而不是继续打补丁

手写图的失效模式是静默的：框架结构变了，数字还在，没有任何机制会发现。 可证伪性是这里唯一重要的性质——一条追不到出处的断言，和一个猜测没有区别。

Chapter 1总体设计与分层

1.1 主线

以框架源码为模型结构的唯一入口；以纯配置描述的原子 op 语义补齐源码无法证明的算子契约； 编译成不可变的 CoreIR；由 BackwardIR → PlacementPlan → ExecutionPlan 三个派生计划层逐步加信息；最后由显存与时间两个只读后端消费。

四类角色必须分清，这是全篇的骨架：

事实源
源码（结构）、配置（语义）、标定（实测量）——只有这三处产生新事实
不可变核
CoreIR：与设备、并行、时序全部无关的逻辑事实
派生层
BackwardIR / PlacementPlan / ExecutionPlan： 各自吃一份策略输入，只读上游、从不回写
只读后端
显存、时间：只消费计划，互不 import，不改 IR

1.2 关节为什么切在这里

分层的判据只有一条：每层只增加一类信息。层数不是越多越好，但关节切错会在某个具体 场景上暴露——所以下面用三个压力测试验它。

压力测试如果关节切错会怎样本分层的表现
重算 同一逻辑算子执行两次、生命周期不同。若把它当结构事实，就要 fork CoreIR 落 BackwardIR：重算节点 = 被复制进反向图的前向节点。CoreIR 不动 ✓
算子融合 融合与否取决于框架版本，看似是环境事实而非模型事实 源码字面调用融合 kernel，且框架版本快照参与语义绑定 ⇒ 确实是编译期可定的源码事实 ✓
交互式 what-if 改一次 tp 若失效整条链，探索器就没法用 改并行只失效 S4/S5；改重算只失效 S3 及其下游；CoreIR（最贵的一层）不动 ✓
为什么源码和配置的分工是这样

源码只提供三样：符号、数据流、attrs 字面值。配置提供全部语义 （(输入 shape, attrs) → 输出）。两者不重叠，所以结构上不可能出现 「这个 shape 该信源码还是信声明」的仲裁问题——「两个真相源」在这个切法下无法复发。

1.3 层的职责边界

层只负责不负责策略输入
S1 语义注册域加载、DSL 校验、冻结成快照看任何一个具体模型—
S2 结构解析源码、绑定语义、产出逻辑事实并行、时序、字节—
S3 反向反向图、重算节点、fan-in 累加在哪、多大RecomputeSpec
S4 布局mesh / shard / local shape / 集合通信生命周期、定价ParallelConfig
S5 执行事件、依赖、流、生命周期、分配释放改逻辑模型调度 + 标定
S6 后端显存：liveness/allocator/OOM；时间：定价/竞争/流水推导上游任何事实硬件 + profile
S7 报告汇总 + 覆盖率 + provenance + confidence隐藏未覆盖项—

1.4 全局不变量

不变量
  1. 单向：派生层只读上游，任何层都不回写上游。
  2. policy-free 核：CoreIR 不含任何策略痕迹（并行度、重算、调度）。
  3. 唯一绑定：一个原子源码调用在一次编译中只能解析到一条 op 语义。
  4. 无 opaque：可执行 IR 中不存在未知算子或不透明节点。
  5. 缺失 ≠ 空：字段缺失（未描述）与显式空值（描述为无）严格区分。
  6. 全或无：预检不过就不产生任何可供后端执行的部分计划。
  7. 身份不靠名字：逻辑值、逻辑存储、放置、物理实例是四个独立 ID（第 6 章）。
  8. provenance 必填：每个进入报告的量都带 provenance；measured 必带标定 key、 assumed 必带依据（第 2 章）。

Chapter 2横切契约：知识分级

2.1 是什么

仿真建模里的量不是同一种知识。本方案给每个量标一个 provenance， 而不是给每一层配一套退化档。三类，闭集：

provenance含义典型量必带缺失时
source_derived 源码 + 算子定义可判定 shape、dtype、alias/inplace、saved 结构、数据流— 阻断
measured 源码里根本不存在，只能实测标定 workspace_bytes、bwd_scratch、kernel duration、allocator 参数 标定 key + 适用边界 缺 key 阻断；命中则带 confidence
assumed 值依赖运行期数据，静态不可判定 MoE 每专家实际负载、专家 capacity、非规则化 placement basis + 方向（上界/下界/标称） 未显式声明即阻断

2.2 为什么分界线在这里

一个直觉的分法是「内存侧要精确、时间侧允许估」。这个分法是错的，两个反例就能推翻：

  • workspace_bytes 在内存侧，却是 kernel 实现属性——源码里没有，只能上机测；
  • MoE 每专家负载在形状侧，却只能假设——它是 router 输出值的函数，不是输入 shape 的函数。

所以真正的分界线是「源码可判定 / 不可判定」，它横穿内存与时间两侧。

为什么必须有 assumed 这一档

被仿真的对象是稀疏模型。topk 之后的实际长度、每专家实际 token 数、动态稀疏注意力的选中数 ——这些在原理上不是(输入 shape, attrs) 的函数，任何静态语义都证明不了。

只有「精确或阻断」两态时，剩下两条路都坏：要么永远阻断（工具对稀疏模型不可用）， 要么偷偷用容量因子顶上（正是本方案禁止的「用缺省值替代未声明」）。 第三态不是妥协，是把已经在做的假设变得可见。

这一档要挡住的失效模式

如果只有阻断，用户为了让工具跑起来，会在骨架里填一个看起来合理的数。 而这个数一旦进了系统就与真值不可区分——它有完整 schema、通过类型检查、 provenance 说它来自用户注册域。结果恰好摧毁了本方案最想要的那条性质。

所以 assumed 必须带 basis，且在报告里独立统计。

2.3 数据结构

# 每个可进报告的量都是这个形状（闭集 tagged union）
Quantity:
  provenance: source_derived | measured | assumed
  value:      <Expr>                 # 受控表达式，见 3.4
  # provenance == measured
  calibration_key: <str>             # 指向标定快照里的条目
  bounds:          <str>             # 适用边界：测过哪些点、哪些维没扫过
  # provenance == assumed
  basis:     <str>                   # 为什么这样假设
  direction: upper | lower | nominal # 偏差方向，报告必须点明

2.4 数据流

provenance 在 S1 声明、随量流经 S2–S5、在 S6 参与 confidence 计算、 在 S7 分类统计。它从不被消掉——任何一层把 assumed 洗成普通数值都是契约违规。

不变量

报告必须能回答：这个峰值里有多少字节来自 measured、多少来自 assumed， 以及每一条的依据是什么。做不到就不是这个方案。

Chapter 3S1 语义层

3.1 是什么

op 语义的唯一词典，以配置文件描述，编译成不可变快照。它不认识任何具体模型—— 它只回答「这个算子是什么」。

3.2 为什么是三个物理隔离的注册域

注册域用途能否改 native加载
Native随仿真器版本发布的内置语义否只读
User补 native 未覆盖的算子否（只能新增）用户目录
NativePatch显式修正一条 native整条替换独立目录 + 开关
为什么不是一张表加优先级

加载顺序决定胜者 = 结果不可复现。 User 声明了 native 已占用的 selector， 必须在加载期直接报冲突，而不是「后者覆盖前者」。

Patch 为什么必须整条替换：字段级 merge 会造出「native 的 shape + user 的 autograd + 默认的 cost」这种没人设计过的混合语义，且没有任何人能对它负责。

3.3 原子 op：一个类型 = 一条形状关系

op 类型必须拆到原子级。反面教材是把 14 种视图语义 （reshape / permute / transpose / squeeze / unsqueeze / concat / stack / split / chunk / slice / tile / roll / broadcast / contiguous）塞进一个 View 类型， 再在代码里用判别字段二次分派——那等于把配置里已有的信息重新读一遍， 而且逼着不同语义共用一条反向规则。

不变量

一个 op 类型只有一条形状关系、一条反向规则、一条布局规则。分派只发生在 selector 绑定， 不发生在语义求值。

3.4 数据结构：op 描述的七个面

描述是纯配置，不含任何代码引用。字段值是受控表达式，由固定函数集求值。

面回答消费者
selector哪个源码符号绑定到本条S2
shape输出形状与输入/attrs 的关系S2–S5
dtypestorage / compute / accum 三类分别是什么S2 / 两后端
storage每个输出是 new / alias / inplaceS2
autograd反向读什么、保存什么、产哪些梯度值S3
placement分片如何沿本算子传播S4
resource逐 phase 的 flops / 访存 / bufferS5 / 时间

  Reshape:

    shape:

      args:  { input: in0, target: attrs.reshape_dims }

    dtype:     { outputs: [same_as(in0)] }

      on_guard_fail: numel_only
      why:    "out.shape[i] = x.shape[dims[i]]（算子定义）"
    # …余下六面同上
为什么组合子在引擎里不算「op 关联了代码」

rel: reshape 里的 reshape 是表达式求值器的原语，与任何具体 op 无关 ——就像配置里写 2*x 不会让人说它关联了代码。判据很清楚： 组合子跨 op 复用（九个原子 op 共用 same_as）， 而 op 独有的知识只有「关系名 + 参数来源 + 守卫 + 退化档」，全是数据。

组合子是闭集，不到 20 个：same_as · broadcast · replace_last · bmm · halve_last · reshape · permute · swap_axes · squeeze · expand_dims · concat · stack · split · chunk · slice · tile · literal · range_len · index_compose · declared。引用不存在的组合子 → 加载即阻断， 并要求说明其算子定义。这是显式、可数、要写理由的扩展点，不是后门。

固定类型系统

类型用途例
IntExpr轴长、元素数、整数属性dim(x,-1)
BoolExpr有限条件分支（必须带 else）attr("causal")
ShapeExpr输出形状broadcast(shape(x),shape(y))
DTypeExpr三类 dtypepromote(dtype(x),dtype(y))

禁止：循环、递归、赋值、可变状态、文件/网络/环境访问、import、用户自定义函数、 运行期改注册表、用缺省值替代未声明项。

3.5 数据流与逻辑流程

  1. 加载三域原始文件 + 框架/运行时版本快照。
  2. schema 解析（closed schema：未知字段、拼错、未知枚举、未知版本全部拒绝）。
  3. 模板展开 → 静态类型检查 → 语义完整性检查（七个面按需齐备）。
  4. 冲突检测：selector 重复、user 侵占 native、patch 目标不存在或 hash 不匹配 → 阻断。
  5. 冻结成不可变快照 + digest（框架版本参与 digest：同一份文件在不同框架版本下不得复用旧快照）。
  6. 此后只做绑定：解析器不再读配置文件、不再展开模板。

Chapter 4S2 结构层

4.1 是什么

读框架源码，产出 CoreIR——一张只含逻辑事实的图：有哪些算子、 它们怎么连、每个值的形状/类型/存储关系是什么。与设备、并行、时序全部无关。

4.2 为什么源码只给结构

前端只做三件事：解析、内联可展开调用、识别原子调用与数据依赖。它不猜任何算子语义—— 一个未绑定的调用进 UnresolvedCall，由 S1 的绑定决定生死。

为什么这个二分是干净的

源码天然知道的是「调用了谁、拿了什么、传了什么常量」；它不知道「这个算子的反向要读什么」。 把前者交给源码、后者交给配置，正好沿着知识的天然边界切。今天那种「形状推断是代码、 部分参数来自源码 attrs」的混合形态，是这条边界没切干净的结果。

4.3 数据结构

CoreIR:
  ops:        [OpInstance]
  values:     [TensorValue]
  storages:   [Storage]
  params:     [ParameterBinding]
  buffers:    [BufferContract]         # 声明式，尚未放置

OpInstance:
  id:          OpId
  semantic_id: SemanticId              # 指向 S1 快照里的那条 op 描述
  inputs:      [TensorId]
  outputs:     [TensorId]              # 可为空（side-effect 算子不许被跳过）
  attrs:       {...}                   # 源码字面值
  dtype:       { compute, accum }

TensorValue:
  id:            TensorId              # 逻辑值身份（见第 6 章）
  shape:         ShapeExpr
  storage_dtype: DType
  storage_id:    StorageId
  layout:        LayoutExpr
  relation:      StorageRelation       # new | alias(base,offset,stride) | inplace(base)

Storage:
  id: StorageId; size: BytesExpr; kind; persistence; alignment

不进 CoreIR：源码文件、行号、调用原文。它们走可剥离的 SourceMap 旁路， 不参与语义 hash——否则换一个注释就会失效整条缓存。

需要澄清的一点

「不承载源码信息」不等于「op 没有可读名字」。算子在模型里的限定名 （形如 attn.indexer.linear_wq_b，由内联帧路径 + 调用点属性名拼成） 是逻辑身份而非源码定位：标定表按它挂载、重算 selector 按它匹配、报告按它可读。 它应当在 OpId 内可解析，而不是只能查旁路。

4.4 数据流与逻辑流程

  1. 从模型配置定位入口，按框架的模块规格解析出本次实际实例化的模块树。
  2. 逐个可展开函数内联，按配置剪掉未命中的条件分支；不可判定的条件即阻断，绝不双走。
  3. 逐语句发射原子调用，用单赋值表记录「哪个变量当前由哪个节点产出」，据此补数据流边。
  4. 每个调用向 S1 快照请求绑定 → 得到 SemanticId；未绑定 → 阻断（第 10 章）。
  5. 按 shape / dtype / storage 三面求值，得到 TensorValue 与 Storage。
  6. 校验 CoreIR 不变量：无 opaque、每输出恰一条存储规则、alias 链无环无悬空、side-effect 算子未被跳过。

Chapter 5S3 反向层

5.1 是什么

把反向图显式化为一层派生 IR。前向节点、反向节点、重算节点是同一种节点类型， 共用同一套形状/类型/布局/资源机器。

5.2 为什么显式化，而不是挂在前向算子上

另一种做法是把反向信息编码成前向算子的「契约字段」（保存哪些输入、产哪些梯度值……）， 再用一个 lowering pass 展开。那样做的代价是：反向值得不到与前向值同等的待遇—— 它们的形状、类型、放置要靠一族专用字段和特殊分支，而不是走同一条路。

显式化之后，一整族契约类退化成图里的普通节点与边：

挂字段的做法显式反向图之后
autograd 契约（保存输入/输出/内部值三个列表）就是图的边
梯度值规格 + phase 存储规则 + phase 值 ID就是 TensorValue + StorageRelation
梯度 fan-in 累加规格就是一个 add 节点——累加本来就是个算子
重算的独立 lowering 路径删除：重算就是被复制进图的前向节点
每个事件/资源对象逐个携带 phase 字段phase 成为图属性
必须守住的性质

BackwardIR 是派生层，RecomputeSpec 是它的输入，digest 独立。 不能把它写进 CoreIR——否则改一次重算配置就失效 CoreIR 缓存，而那是最贵的一层， 交互式 what-if 会因此不可用。

5.3 数据结构

BackwardIR:                            # = f(CoreIR, RecomputeSpec)
  nodes: [Node]                        # 与 CoreIR 同构：phase ∈ {forward,backward,recompute}
  edges: [(NodeId, NodeId)]
  release: [ReleaseJoin]               # 由「最后一个 reader」的边直接推出，不再手写

Node:                                  # 三类节点唯一的区别是 phase 与来源
  id:          NodeId
  semantic_id: SemanticId              # 重算节点与其前向节点**同一个** SemanticId
  phase:       forward | backward | recompute
  origin:      NodeId?                 # 重算/反向节点回指其前向节点
  inputs/outputs/attrs                 # 同 CoreIR

5.4 数据流与逻辑流程

  1. 按 CoreIR 拓扑逆序，为每个可微算子生成反向节点；不可微算子（比较、常量、detach）不生成。
  2. 反向节点的输入按 autograd 面解析：需要保存的前向值在图上连出跨相边—— 这条边同时就是它的生命周期依据。
  3. 一个前向值收到多个下游梯度贡献时，插入 add 节点；上游只绑定累加结果这一个值。
  4. 按 RecomputeSpec 选中的区域，把该区域的前向节点复制进反向图 （同 SemanticId、新 NodeId、phase=recompute、 origin 回指），插在该区域反向节点之前。
  5. 校验：每个梯度边恰一个 producer；重算节点的输入在其插入点可达；释放点在偏序上晚于所有 reader。

Chapter 6身份体系

6.1 是什么与为什么

四个独立 ID。存在的理由是一句反命题：用名字推断物理复用一定同时犯两个方向的错。

ID是什么回答的问题
TensorId逻辑值身份（一次赋值 = 一个）这是同一个值，还是同名的新值？
StorageId逻辑存储 / alias 等价类这两个值共享同一块存储吗？
StoragePlacementIdrank / stage 上的放置模板它在哪张卡上、切成多大？
StorageInstanceId某次执行 lifetime 的物理分配这次分配占多少字节、什么时候还？
按名字去重会同时错两个方向 
x = f(a)          # 逻辑值 1，存储 1
y = x.view(...)    # 逻辑值 2，存储 1   ← 别名，零分配
x = g(y)          # 逻辑值 3，存储 2   ← 同名，但是新值

按名字首见定型：值 1 与值 3 被当成同一个（少算），值 1 与值 2 被当成两次分配（多算）。 四层身份把这两类错误一起消掉，而且让「零字节别名」可表达——这是桶式记账做不到的。

Chapter 7S4 布局层

7.1 是什么

吃并行配置，为每个值算出：每根轴被谁切了、本地形状是多少、哪里需要插集合通信。

7.2 为什么它必须是独立一层，且必须有声明通道

独立的理由是变化率：并行策略是 what-if 的主要变量，把它隔离出来， 改 tp 只需重算这一层及其下游。

可推导性的边界（本方案相对 v1 的修正）

「placement 可由模块语义推导」只在框架的切分本身是规则化、且我们复刻了那套规则时成立。 半自动/自动并行的策略传播是一个求解器，不是一组规则。

把策略搜索器列为非目标是对的；但排除求解器之后，必须允许 placement 作为声明输入 ——从源码的布局标注读出（source_derived），或由用户声明（assumed）。 只有「推导」一种模式的设计，对那类框架在原理上无解。

7.3 数据结构

PlacementPlan:                         # = f(BackwardIR, ParallelConfig)
  values:      [ValuePlacement]
  storages:    [StoragePlacement]
  buffers:     [BufferPlacement]
  collectives: [CollectivePlan]

ValuePlacement:
  value:       ValueRef                # 覆盖 primal 与梯度，统一引用
  shard:       { axis_key: mesh_axis }  # tp / ep / cp / sp
  local_shape: Shape
  layout:      LayoutSignature         # 含 stride/offset/对齐（进 profile 签名）
  source:      derived | declared      # ← 7.2 的声明通道
  provenance:  source_derived | assumed

7.4 数据流与逻辑流程

  1. 段入口播种：外部输入若含序列轴且启用序列并行，标记为序列驻留。
  2. 沿数据流传播每个值的分片状态；规则来自 S1 的 placement 面（列并行产出特征载体、 行并行消耗载体、序列并行权重不切）。
  3. 汇合点取并集；序列驻留状态分歧 → 在驻留侧注入布局重分布通信。
  4. 模块语义要求的通信按规则注入（列并行入口聚合、行并行出口归约/散播）。
  5. 无法推导的值：走声明通道；既无推导也无声明 → 阻断，逐条记录。
  6. 校验：载体歧义、列∘列、行前无列、不整除 → 全部阻断（不许悄悄取整）。
不变量

轴代入规则只有一份实现。两个后端各自实现一遍的必然结果是分道——而分道不会 被任何现有测试发现，因为没有断言把两者放在一起看。

Chapter 8S5 执行层

8.1 是什么

把「逻辑上活多久」变成「事件序上什么时候申请、什么时候释放」，并为每个算子实例生成 自包含的定价请求。

8.2 为什么两个视图都必须自包含

为什么后端不许回读上游

后端一旦回读 IR/计划去补信息，它的 profile / cache key 就随上游结构变化而失效—— 换一次上游重构，实测复用会静默失灵，而失灵的表现是「命中率下降」，不是报错。 代价是执行计划变大（信息被复制进去），这是有意的空间换解耦。

8.3 数据结构

ExecutionPlan:                         # = f(BackwardIR, PlacementPlan, 调度配置, 标定)
  targets:   [ExecutionTarget]         # rank / device / stage / 资源域
  events:    [ExecEvent]               # kind / target / stream / deps
  memory:    MemoryEventView           # 给显存后端的自包含视图
  requests:  [ResourceRequest]         # 给时间后端的自包含定价请求
  instances: [StorageInstance]         # StorageInstanceId + epoch

MemoryEventView:                       # 自包含：不依赖时间后端的内部状态
  events:      [Allocate|Bind|Use|Pin|Retire|Free]
  descriptors: [AllocationDescriptor]  # 每个 Allocate 可唯一解析出字节/域/池/对齐
  order:       dependency + stream 偏序
  policy:      MemorySchedulePolicy?   # 可选；缺省用偏序的确定性拓扑

ResourceRequest:                       # 自包含：时间后端不回读 CoreIR/PlacementPlan
  target: ExecutionTargetId
  work:   { flops, special_ops, reduction_ops }   # 分 model / executed 两套
  traffic:{ memory, transport }
  pricing:PricingDescriptor            # 含 compute/accum dtype、cost family、签名基
  provenance: 逐量携带（见第 2 章）

8.4 数据流与逻辑流程

  1. 按调度（1F1B / 交错虚拟流水）展开 (stage × microbatch × 节点)；重算节点已在 S3 入图，此处无特例。
  2. 为每个值实例分配 StorageInstanceId：alias 归并到 root（零分配）， inplace 在变更点终结旧值，重算再物化用新 epoch。
  3. 由 S3 的释放点偏序推出 Retire/Free；被保存的值以 Pin 延寿， 不改变其字节（需要独立字节的一律建成内部保存值）。
  4. 为每个 BufferContract 按放置结果解析本地字节，落成半开区间的申请/释放对。
  5. 生成资源请求：逐量带 provenance，measured 项在此绑定标定 key。
  6. 联合预检：所选后端需要的能力是否齐备、事件是否不重不漏、偏序是否无环。不过则不产出任何部分计划。

Chapter 9S6 后端与 S7 报告

9.1 显存后端

只消费 MemoryEventView。核心状态是「当前在世的物理实例集合」， 按事件推进、按池与对齐规则模拟申请释放，给出已分配/已保留峰值与 OOM 判定及首次失败证据。 结束前做终审：没有残留未释放的非持久实例、没有未 lower 的高层事件。

9.2 时间后端

只消费 ResourceRequest + 硬件/profile 快照。两级离散事件仿真保持不变 （段内多流 → 全局调度）。定价按退化链：命中兼容实测 → 形状/类型插值 → 已标定族模型 → 理论 roofline；每档记 provenance 与 confidence，参数不全则阻断，绝不静默变成零成本或纯带宽。

9.3 报告

不变量

两个后端不共同构造报告，由汇总器聚合。报告必须分别统计三类 provenance 的覆盖率， 并把 assumed 项的依据与偏差方向逐条列出。不允许把未覆盖项藏起来。

Chapter 10阻断与用户闭环

10.1 阻断的范围（相对 v1 收紧了定义）

情形处理为什么
未注册 op阻断 + 生成骨架 语义未知时任何数都是编的；且这种情况罕见（新 kernel 才会遇到）
已注册，含 measured 量放行 + 报告标注 标定值是已声明的实测事实，不是猜测
已注册，含 assumed 量放行 + 报告标注依据与方向 否则第 2 章的第三态无处落脚，稀疏模型永远跑不起来
形状/类型解不出阻断 source_derived 缺失即不可判定
为什么这两件事必须分开

把它们混在同一条不变量里（「不完整就阻断」）会导致：要么 assumed 无处安放， 要么为了让工具能跑而把 assumed 伪装成 source_derived。后者是最坏的结果。

10.2 闭环流程

  1. 发现未绑定调用 → 阻断，并输出：符号、各输入的形状与类型、赋值目标、两个注册域的查找结果。
  2. 生成骨架：只填能从调用证明的（selector、输入、attrs），其余全部 REQUIRED 占位。
  3. 用户补完 → 校验 → 解释（打印该 op 展开后的完整七面语义，供人复核）。
  4. 快照 digest 更新 → 上游产物缓存失效 → 重新编译 → 联合预检 → 开始仿真。

骨架里不含源码文件与行号——那些只出现在诊断输出，避免用户配置与源码位置耦合。

Chapter 11验收与迁移

11.1 对照物只能是真机

一条方法论错误必须避免

迁移期做新旧双跑是必要的，但不能用旧路径判对错。以旧路径为准绳，等于把旧路径的已知偏差 编码成新系统的验收标准。

一个仿真器的正确性定义只能来自被仿真的对象，不能来自它的前一版。 双跑的正确用途是变更归因（哪些数变了、为什么），判对错必须对真机实测。

门断言性质
真机对照逐 stage 峰值、逐层驻留、step time 与实测比值；实测数据带指纹校验，不得编辑唯一对错判据
结构不变量×1 于层数、×1 于微批数这类结构性关系必须由模型导出而非被公式告知正确性
轴代入一致两个后端路径对同一符号形状 × 同一并行度，本地元素数必须逐字节相等防分道
provenance 闭合报告里每个字节可归到三类之一；assumed 项均有依据诚实性
阻断有效性参数化删除任一必填字段 → 必须阻断；显式空值 ≠ 缺失安全性
后端隔离两后端双向 import 禁令；后端不读源码/配置/注册表解耦
新旧双跑逐项差异归因，已知设计修正列入 accepted delta归因，非判据

11.2 迁移策略

不做全量重写（数值变化无法归因），不做长期双轨（两个真相源必然漂移）。 采用适配层 + 按算子族收编 + 双跑归因，每收编一族就删掉对应旧分支。

阶段内容该阶段的门
1语义基础设施：类型系统、组合子库、DSL 编译器、三注册域加载期阻断用例全绿
2适配层：把现有语义表接进新描述，可证明部分数值不变；由缺字段/默认零产生的值一律标 legacy 假设，未经显式收编不得通过完整性门真机对照不劣化
3按族收编：视图/类型转换/比较 → 逐元素/归一化 → 矩乘 → 注意力 → MoE → 集合通信 → 融合每族收编后真机对照 + 双跑归因
4CoreIR + BackwardIR + 两个计划层不变量校验 + 轴代入一致门
5后端切换：显存改吃事件视图，时间经适配复用现有两级仿真真机对照成为权威判据
6开放用户通道：注册、校验、解释、骨架生成闭环用例全绿
7收口：删除旧分支，只留兼容 API全门绿

11.3 起点距离必须先量化

诚实边界

「可执行 IR 中不存在 opaque 节点」是目标态的不变量，不是今天的状态。启动阶段 2 之前 必须先量化并公布起点距离：当前抽取链上有多少调用还绑不上语义、级联根在哪几处、 哪些量在原理上读不出（融合 kernel 自身输出的形状在编译产物里，不在源码里）。 不量化就开工，等于把「什么时候算做完」变成一个没人能回答的问题。

Chapter 12决策记录与边界

12.1 决策记录

#决策关键理由
D1结构从框架源码抽取，是唯一结构源手写图的失效是静默的；可证伪性优先
D2op 语义用纯配置描述，不开放代码插件可静态校验、可版本化、用户可扩展
D3op 类型拆到原子级（一类型 = 一条形状关系）消灭代码里的二次分派；避免不同语义共用一条反向规则
D4三注册域物理隔离；patch 整条替换 + 版本/hash 门禁加载顺序决定胜者 = 不可复现
D5未注册 op 硬阻断 + 生成骨架语义未知时任何数都是编的
D6provenance 三分（source_derived / measured / assumed）作为全 IR 横切契约分界线是「源码可判定与否」，横穿内存与时间；稀疏模型必须有第三态
D7BackwardIR 为独立派生层，重算节点入图三类节点同构；删掉一族契约类与一条 lowering 路径；CoreIR 保持 policy-free
D8四层身份，禁止按名字推断复用名称去重必然同时少算与多算
D9dtype 分 storage / compute / accum，编译期求值，无退化档它是 source_derived；缺依据即阻断，不默认继承首输入
D10placement 有推导与声明两种输入模式非规则化切分的框架在原理上推不出来
D11轴代入只有一份实现两份实现必然分道，且不会被任何现有测试发现
D12两后端只读、互不 import、自包含视图后端回读上游会让 profile 复用静默失灵
D13验收对照物是真机；新旧双跑只做归因正确性定义只能来自被仿真对象

其中 D6 / D7 / D10 / D13 是本版相对 v1 的实质改动，其余为承接。

12.2 非目标

  • 不把自动并行策略搜索器纳入核心（但因此必须有 placement 声明通道，见 D10）。
  • 配置不执行任意代码，不开放语法扩展或解释器插件。
  • 基础语义库不保存某型号设备上的实测耗时（那属于标定/profile）。
  • 不追求一次性删除全部旧路径。

12.3 诚实边界

这套设计做不到的事
  • 融合 kernel 自身输出的保存集：末轴在编译产物里、不在源码里。声明通道能承载它， 但没人声明时就是 Unknown——照样不给数，不猜。
  • 数据依赖量的精确值：MoE 实际负载只能是 assumed。报告能说清方向与依据， 但不能把它变成精确值。
  • 反馈回路长度：干净分层的固有代价是第一个可与现实比对的数字要等整条链。 适配层 + 按族收编是缓解，不是消除——所以阶段 2 的门必须是真机而非旧路径。
  • 覆盖面：目标态不承诺一次覆盖所有模型族；未覆盖的层型必须显式阻断，不产空层。

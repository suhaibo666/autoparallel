Chapter 0导读与基线

这份文档回答一个问题：如果从原理出发重新设计这个仿真器的模型表示，其目标形态应当如何。它不是现有代码的改造清单，而是目标形态的分层规范——每一层说明四项内容：是什么、为什么这样切、主要数据结构、数据流与逻辑流程。

要解决的四个问题

问题当前形态本方案
模型演进速度 Op 图与 saves=[...] 手写在 Python 中，框架代码变更后容易静默失效 结构从源码抽取，重跑编译即更新
未知算子 三种不一致结果：抛错 / 只进 opaque_calls / 透传首输入 shape 统一阻断 + 生成待填骨架
两条建模链彼此独立 显存侧使用手写图，时间侧使用抽取图；轴代入与反向语义分别实现 共享 Structure、Backward 与 Placement，后端只保留各自的计算口径
不确定量缺少统一表达 时间侧设有分级回退与 confidence；形状/内存侧只有「精确或阻断」 provenance 作为全 IR 横切契约（第 2 章）
为什么需要重构，而不是继续局部修补

手写图的失效模式是静默的：框架结构已经变化，旧结果仍可继续输出，却没有机制能够发现。因此，可证伪性是这里最关键的性质——无法追溯来源的结论，与猜测没有区别。

Chapter 1总体设计与分层

1.1 主线

以框架源码为模型结构的唯一入口；以纯配置描述的原子 Op 语义补齐源码无法证明的算子契约；编译成不可变的 CoreIR；由 BackwardIR → PlacementPlan → ExecutionPlan 三个派生计划层逐步加信息；最后由显存与时间两个只读后端消费。

四类角色必须分清，这是全篇的骨架：

事实源
源码（结构）、配置（语义）、标定（实测量）——只有这三类输入产生新事实
不可变核
CoreIR：与设备、并行、时序全部无关的逻辑事实
派生层
BackwardIR / PlacementPlan / ExecutionPlan：各自接收一类策略输入，只读上游、从不回写
只读后端
显存、时间：只消费计划，互不 import，不改 IR

1.2 为什么在这里划分层级边界

分层的判据只有一条：每层只增加一类信息。层数并非越多越好，但边界设置不当会在具体场景中暴露问题。下面通过三个压力场景验证这一划分。

压力测试如果层级边界设置不当本分层的表现
重算 同一逻辑算子执行两次且生命周期不同。若将其视为结构事实，就必须生成 CoreIR 分支 落 BackwardIR：重算节点 = 被复制进反向图的前向节点。CoreIR 不动 ✓
算子融合 融合与否取决于框架版本，看似是环境事实而非模型事实 源码中直接调用融合 kernel，且框架版本快照参与语义绑定，因此它属于编译期可确定的源码事实 ✓
交互式 what-if 如果修改一次 tp 就使整条链失效，系统将无法支持交互式探索 修改并行配置只使 S4/S5 失效；修改重算配置只使 S3 及其下游失效；CoreIR（编译成本最高的一层）保持不变 ✓
为什么这样划分源码与配置的职责

源码只提供三类信息：符号、数据流、attrs 字面值。配置提供完整语义（(输入 shape, attrs) → 输出）。两者不重叠，所以结构上不可能出现「这个 shape 应采用源码还是声明」的仲裁问题——这种划分从结构上消除了「两个真相源」。

1.3 层的职责边界

层只负责不负责策略输入
S1 语义注册域加载、DSL 校验、冻结成快照解析具体模型实例—
S2 结构解析源码、绑定语义、产出逻辑事实并行策略、执行时序和物理字节—
S3 反向反向图、重算节点、fan-in 累加放置位置和本地规模RecomputeSpec
S4 布局mesh / shard / local shape / 集合通信生命周期、定价ParallelConfig
S5 执行事件、依赖、流、生命周期、分配释放改逻辑模型调度 + 标定
S6 后端显存：liveness/allocator/OOM；时间：定价/竞争/流水重新推导任何上游事实硬件 + profile
S7 报告汇总 + 覆盖率 + provenance + confidence隐藏未覆盖项—

1.4 全局不变量

不变量
  1. 单向：派生层只读上游，任何层都不回写上游。
  2. policy-free 核：CoreIR 不含任何策略痕迹（并行度、重算、调度）。
  3. 唯一绑定：一个原子源码调用在一次编译中只能解析到一条 Op 语义。
  4. 无 opaque：可执行 IR 中不存在未知算子或不透明节点。
  5. 缺失 ≠ 空：字段缺失（未描述）与显式空值（描述为无）严格区分。
  6. 全或无：预检不过就不产生任何可供后端执行的部分计划。
  7. 身份不靠名字：逻辑值、逻辑存储、放置、物理实例是四个独立 ID（第 6 章）。
  8. provenance 必填：每个进入报告的量都带 provenance；measured 必带标定 key、assumed 必带依据（第 2 章）。

Chapter 2横切契约：知识分级

2.1 是什么

仿真建模中的量具有不同的知识来源。本方案为每个量标注 provenance，而不是为每一层设置统一的回退等级。类型限定为以下三种，构成闭集：

provenance含义典型量必带缺失时
source_derived 源码 + 算子定义可判定 shape、dtype、alias/inplace、saved 结构、数据流— 阻断
measured 源码中不包含，只能通过实测标定 workspace_bytes、bwd_scratch、kernel duration、allocator 参数 标定 key + 适用边界 缺 key 阻断；命中则带 confidence
assumed 值依赖运行期数据，静态不可判定 MoE 每专家实际负载、专家 capacity、非规则化 placement basis + 方向（上界/下界/标称） 未显式声明即阻断

2.2 为什么分界线在这里

一种直观的划分是「内存侧要求精确、时间侧允许估算」。这种划分并不成立，两个反例即可说明：

  • workspace_bytes 在内存侧，却是 kernel 实现属性——源码里没有，只能上机测；
  • MoE 每专家负载在形状侧，却只能假设——它是 router 输出值的函数，不是输入 shape 的函数。

所以真正的分界线是「源码可判定 / 不可判定」，它横穿内存与时间两侧。

为什么必须引入 assumed 类型

被仿真的对象是稀疏模型。top-k 操作后的实际长度、每个专家处理的实际 token 数、动态稀疏注意力的选中数 ——这些在原理上不是(输入 shape, attrs) 的函数，任何静态语义都证明不了。

如果系统只有「精确或阻断」两种状态，则两种处理方式都不可取：要么始终阻断（工具无法用于稀疏模型），要么隐式使用容量因子代替真实值（正是本方案禁止的「用缺省值替代未声明」）。第三种状态不是妥协，而是将原本隐含的假设显式化。

这一档要挡住的失效模式

如果只有阻断，用户为了让仿真继续执行，可能会在骨架中填写一个表面合理的数值。该数值一旦进入系统，就会与真值不可区分——它具有完整 schema、通过类型检查， provenance 也表明它来自用户注册域。这会破坏本方案最重视的可追溯性。

所以 assumed 必须带 basis，且在报告里独立统计。

2.3 数据结构

# 每个可进入报告的量都采用这一结构（闭集 tagged union）
Quantity:
  provenance: source_derived | measured | assumed
  value:      <Expr>                 # 受控表达式，见 3.4
  # provenance == measured
  calibration_key: <str>             # 指向标定快照里的条目
  bounds:          <str>             # 适用边界：测过哪些点、哪些维没扫过
  # provenance == assumed
  basis:     <str>                   # 为什么这样假设
  direction: upper | lower | nominal # 偏差方向，报告必须点明

2.4 数据流

provenance 在 S1 声明，随量流经 S2–S5，在 S6 参与 confidence 计算，并在 S7 分类统计。它不得丢失——任何一层将 assumed 转换成普通数值都属于契约违规。

不变量

报告必须能回答：这个峰值里有多少字节来自 measured、多少来自 assumed，以及每一项的依据是什么。若无法回答，说明实现不符合本方案。

Chapter 3S1 语义层

3.1 是什么

这是 Op 语义的唯一词典：语义通过配置文件描述，并编译成不可变快照。它不依赖任何具体模型，只回答「这个算子是什么」。

3.2 为什么是三个物理隔离的注册域

注册域用途能否改 native加载
Native随仿真器版本发布的内置语义否只读
User补 native 未覆盖的算子否（只能新增）用户目录
NativePatch显式修正一条 native整条替换独立目录 + 开关
为什么不采用单表加优先级

如果由加载顺序决定最终生效项，结果将不可复现。 User 声明了 native 已占用的 selector，必须在加载期直接报冲突，而不是「后者覆盖前者」。

Patch 为什么必须整条替换：字段级 merge 会产生「native 的 shape + user 的 autograd + 默认的 cost」这类未经整体设计和验证的混合语义，无法明确其责任归属。

3.3 原子 Op：一种类型对应一条形状关系

Op 类型必须拆到原子级。不推荐的做法是将 14 种视图语义（reshape / permute / transpose / squeeze / unsqueeze / concat / stack / split / chunk / slice / tile / roll / broadcast / contiguous）合并为一个 View 类型，再在代码中通过判别字段进行二次分派。这相当于重新解析配置中已有的信息，并迫使不同语义共用一条反向规则。

不变量

一个 Op 类型只对应一条形状关系、一条反向规则和一条布局规则。分派只发生在 selector 绑定阶段，不发生在语义求值。

3.4 数据结构：Op 描述的七个面

描述是纯配置，不含任何代码引用。字段值是受控表达式，由固定函数集求值。

面回答消费者
selector哪个源码符号绑定到本条S2
shape输出形状与输入/attrs 的关系S2–S5
dtypestorage / compute / accum 三类分别是什么S2 / 两后端
storage每个输出是 new / alias / inplaceS2
autograd反向读什么、保存什么、产哪些梯度值S3
placement分片如何沿本算子传播S4
resource逐 phase 的 flops / 访存 / bufferS5 / 时间

    shape:

      on_guard_fail: numel_only

    # …余下六面同上
为什么引擎中的组合子不等于「Op 关联了代码」

rel: reshape 里的 reshape 是表达式求值器的原语，与任何具体 Op 无关 ——正如在配置中写 2*x 并不意味着配置关联了代码。判据很明确：组合子可以跨 Op 复用（九个原子 Op 共用 same_as），而 Op 独有的知识只有「关系名 + 参数来源 + 守卫 + 回退策略」，这些内容全部以数据表示。

组合子构成闭集，当前共 20 个：same_as · broadcast · replace_last · bmm · halve_last · reshape · permute · swap_axes · squeeze · expand_dims · concat · stack · split · chunk · slice · tile · literal · range_len · index_compose · declared。引用不存在的组合子 → 加载即阻断，并要求说明其算子定义。这是显式、数量可控且必须说明理由的扩展点，不是隐式代码扩展入口。

固定类型系统

类型用途例
IntExpr轴长、元素数、整数属性dim(x,-1)
BoolExpr有限条件分支（必须带 else）attr("causal")
ShapeExpr输出形状broadcast(shape(x),shape(y))
DTypeExpr三类 dtypepromote(dtype(x),dtype(y))
BytesExprbuffer 与通信字节numel(x)*sizeof(dtype(x))
ValueRefExprprimal / 梯度 / 内部值引用grad_output(0)

禁止：循环、递归、赋值、可变状态、文件/网络/环境访问、import、用户自定义函数、运行期改注册表、用缺省值替代未声明项。

3.5 数据流与逻辑流程

  1. 加载三个注册域的原始文件及框架/运行时版本快照。
  2. 解析 schema（closed schema：未知字段、字段拼写错误、未知枚举和未知版本全部拒绝）。
  3. 模板展开 → 静态类型检查 → 语义完整性检查（七个面按需齐备）。
  4. 冲突检测：selector 重复、User selector 与 Native 冲突、patch 目标不存在或 hash 不匹配 → 阻断。
  5. 冻结成不可变快照 + digest（框架版本参与 digest：同一份文件在不同框架版本下不得复用旧快照）。
  6. 此后只做绑定：解析器不再读配置文件、不再展开模板。

Chapter 4S2 结构层

4.1 是什么

读取框架源码并产出 CoreIR——一张只包含逻辑事实的图：有哪些算子、算子之间如何连接，以及每个值的形状、类型和存储关系。它与设备、并行和时序全部无关。

4.2 为什么源码只给结构

前端只做三件事：解析源码、内联可展开调用、识别原子调用与数据依赖。它不推断任何算子语义—— 未绑定的调用进入 UnresolvedCall，由 S1 的绑定结果决定该调用能否进入可执行 IR。

为什么这种职责划分清晰

源码天然知道的是「调用了谁、拿了什么、传了什么常量」；它不知道「这个算子的反向要读什么」。将前者交给源码、后者交给配置，正好沿着知识的天然边界划分职责。当前「形状推断由代码实现、部分参数来自源码 attrs」的混合形态，正是这条边界划分不清的结果。

4.3 数据结构

CoreIR:
  ops:        [OpInstance]
  values:     [TensorValue]
  storages:   [Storage]
  params:     [ParameterBinding]
  buffers:    [BufferContract]         # 声明式，尚未放置

OpInstance:
  id:          OpId
  semantic_id: SemanticId              # 指向 S1 快照中的对应 Op 描述
  inputs:      [TensorId]
  outputs:     [TensorId]              # 可为空（side-effect 算子不得被跳过）
  attrs:       {...}                   # 源码字面值
  dtype:       { compute, accum }

TensorValue:
  id:            TensorId              # 逻辑值身份（见第 6 章）
  shape:         ShapeExpr
  storage_dtype: DType
  storage_id:    StorageId
  layout:        LayoutExpr
  relation:      StorageRelation       # new | alias(base,offset,stride) | inplace(base)

Storage:
  id: StorageId; size: BytesExpr; kind; persistence; alignment

CoreIR 不包含源码文件、行号和调用原文。它们通过可剥离的 SourceMap 旁路传递，不参与语义 hash——否则换一个注释就会失效整条缓存。

需要澄清的一点

「不承载源码信息」不等于「Op 没有可读名称」。算子在模型中的限定名（形如 attn.indexer.linear_wq_b，由内联帧路径 + 调用点属性名拼成）是逻辑身份而非源码定位：标定表以它为索引挂载，重算 selector 按它匹配，报告也用它提供可读名称。它应当能够从 OpId 中解析，而不是只能通过旁路查询。

4.4 数据流与逻辑流程

  1. 从模型配置定位入口，按框架的模块规格解析出本次实际实例化的模块树。
  2. 逐个内联可展开函数，并按配置剪除未命中的条件分支；条件不可判定时立即阻断，禁止同时保留两条分支。
  3. 按语句生成原子调用节点，用单赋值表记录「当前变量由哪个节点产出」，据此补全数据流边。
  4. 每个调用都与 S1 快照执行语义绑定 → 得到 SemanticId；未绑定 → 阻断（第 10 章）。
  5. 按 shape / dtype / storage 三面求值，得到 TensorValue 与 Storage。
  6. 校验 CoreIR 不变量：无 opaque、每输出恰一条存储规则、alias 链无环无悬空、side-effect 算子未被跳过。

Chapter 5S3 反向层

5.1 是什么

将反向图显式化为一层派生 IR。前向节点、反向节点和重算节点使用同一种节点类型，共用同一套形状、类型、布局与资源计算机制。

5.2 为什么采用显式反向图，而不是将反向信息挂在前向算子上

另一种做法是把反向信息编码成前向算子的「契约字段」（保存哪些输入、产哪些梯度值……），再通过 lowering pass 展开。这样做的代价是：反向值无法与前向值采用同一套表示—— 它们的形状、类型和放置需要依赖一组专用字段与特殊分支，而不能复用同一条处理链。

显式化之后，这一组契约类可以统一表示为图中的普通节点与边：

挂字段的做法显式反向图之后
autograd 契约（保存输入/输出/内部值三个列表）就是图的边
梯度值规格 + phase 存储规则 + phase 值 ID就是 TensorValue + StorageRelation
梯度 fan-in 累加规格表现为一个 add 节点——累加本身就是算子计算
重算的独立 lowering 路径无需保留：重算就是被复制进图的前向节点
每个事件/资源对象分别携带 phase 字段phase 成为图属性
必须保持的性质

BackwardIR 是派生层，RecomputeSpec 是它的输入，digest 独立。不能将它写入 CoreIR——否则每次修改重算配置都会使 CoreIR 缓存失效，而 CoreIR 是编译成本最高的一层，系统也将无法支持交互式 what-if。

5.3 数据结构

BackwardIR:                            # = f(CoreIR, RecomputeSpec)
  nodes: [Node]                        # 与 CoreIR 同构：phase ∈ {forward,backward,recompute}
  edges: [(NodeId, NodeId)]
  release: [ReleaseJoin]               # 由「最后一个 reader」的边直接推出，不再手写

Node:                                  # 三类节点唯一的区别是 phase 与来源
  id:          NodeId
  semantic_id: SemanticId              # 重算节点与其前向节点「同一个」SemanticId
  phase:       forward | backward | recompute
  origin:      NodeId?                 # 重算/反向节点回指其前向节点
  inputs/outputs/attrs                 # 同 CoreIR

5.4 数据流与逻辑流程

  1. 按 CoreIR 拓扑逆序，为每个可微算子生成反向节点；不可微算子（比较、常量、detach）不生成。
  2. 反向节点的输入按 autograd 面解析：需要保存的前向值在图上连出跨相边—— 这条边同时就是它的生命周期依据。
  3. 一个前向值收到多个下游梯度贡献时，插入 add 节点；上游只绑定唯一的累加结果。
  4. 按 RecomputeSpec 选中的区域，把该区域的前向节点复制进反向图（同 SemanticId、新 NodeId、phase=recompute、origin 回指），插在该区域反向节点之前。
  5. 校验：每个梯度边恰一个 producer；重算节点的输入在其插入点可达；释放点在偏序上晚于所有 reader。

Chapter 6身份体系

6.1 是什么与为什么

系统需要四类独立 ID，原因是：使用名称推断物理复用，必然会在两个方向上同时出错。

ID是什么回答的问题
TensorId逻辑值身份（一次赋值 = 一个）这是同一个值，还是同名的新值？
StorageId逻辑存储 / alias 等价类这两个值共享同一块存储吗？
StoragePlacementIdrank / stage 上的放置模板它在哪张卡上、切成多大？
StorageInstanceId某次执行 lifetime 的物理分配这次分配占多少字节、何时释放？
按名称去重会在两个方向上同时出错 
x = f(a)          # 逻辑值 1，存储 1
y = x.view(...)    # 逻辑值 2，存储 1   ← 别名，零分配
x = g(y)          # 逻辑值 3，存储 2   ← 同名，但是新值

如果按名称采用首次出现时的定义，值 1 与值 3 会被视为同一个值（少算），值 1 与值 2 会被视为两次分配（多算）。四层身份能够同时消除这两类错误，并使「零字节别名」可表达——这是基于分桶的记账方式无法做到的。

Chapter 7S4 布局层

7.1 是什么

布局层接收并行配置，并为每个值计算：各维度由哪个 mesh 轴切分、本地形状是多少，以及需要在哪些位置插入集合通信。

7.2 为什么它必须独立成层，并提供声明通道

独立成层的依据是变化频率：并行策略是 what-if 的主要变量。将其隔离后，修改 tp 只需重新计算这一层及其下游。

可推导性的边界（本方案相对 v1 的修正）

「placement 可由模块语义推导」只在框架的切分本身是规则化、且我们复刻了那套规则时成立。半自动/自动并行的策略传播是一个求解器，不是一组规则。

将策略搜索器列为非目标是合理的；但排除求解器之后，必须允许 placement 作为声明输入 ——可以从源码布局标注中读取（source_derived），也可以由用户声明（assumed）。如果设计只支持「推导」这一种模式，就无法覆盖此类框架。

7.3 数据结构

PlacementPlan:                         # = f(BackwardIR, ParallelConfig)
  values:      [ValuePlacement]
  storages:    [StoragePlacement]
  buffers:     [BufferPlacement]
  collectives: [CollectivePlan]

ValuePlacement:
  value:       ValueRef                # 覆盖 primal 与梯度，统一引用
  shard:       { axis_key: mesh_axis }  # tp / ep / cp / sp
  local_shape: Shape
  layout:      LayoutSignature         # 含 stride/offset/对齐（进 profile 签名）
  source:      derived | declared      # ← 7.2 的声明通道
  provenance:  source_derived | assumed

7.4 数据流与逻辑流程

  1. 在段入口初始化分片状态：外部输入若包含序列轴且启用序列并行，则标记为序列驻留。
  2. 沿数据流传播每个值的分片状态；规则来自 S1 的 placement 面（列并行产出特征载体、行并行消耗载体、序列并行权重不切）。
  3. 在汇合点合并状态；如果序列驻留状态存在分歧，则在驻留侧注入布局重分布通信。
  4. 模块语义要求的通信按规则注入（列并行入口聚合、行并行出口归约/散播）。
  5. 无法推导的值：走声明通道；既无推导也无声明 → 阻断，逐条记录。
  6. 校验：载体歧义、列∘列、行并行前缺少列并行、不整除 → 全部阻断（禁止隐式取整）。
不变量

轴代入规则只能有一份实现。如果两个后端分别实现，结果必然产生分歧；而现有测试无法发现这种分歧，因为没有断言对两者进行统一比较。

Chapter 8S5 执行层

8.1 是什么

执行层将「逻辑生命周期」转换为明确的申请与释放事件顺序，并为每个算子实例生成自包含的定价请求。

8.2 为什么两个视图都必须自包含

为什么后端不得回读上游

后端一旦回读 IR 或计划来补充信息，其 profile / cache key 就会随上游结构变化而失效—— 上游每次重构都可能使实测画像复用静默失效，而外在表现只是「命中率下降」，并不会报错。代价是执行计划体积增大（信息需要复制到计划中），这是有意以空间开销换取解耦。

8.3 数据结构

ExecutionPlan:                         # = f(BackwardIR, PlacementPlan, 调度配置, 标定)
  targets:   [ExecutionTarget]         # rank / device / stage / 资源域
  events:    [ExecEvent]               # kind / target / stream / deps
  memory:    MemoryEventView           # 给显存后端的自包含视图
  requests:  [ResourceRequest]         # 给时间后端的自包含定价请求
  instances: [StorageInstance]         # StorageInstanceId + epoch

MemoryEventView:                       # 自包含：不依赖时间后端的内部状态
  events:      [Allocate|Bind|Use|Pin|Retire|Free]
  descriptors: [AllocationDescriptor]  # 每个 Allocate 可唯一解析出字节/域/池/对齐
  order:       dependency + stream 偏序
  policy:      MemorySchedulePolicy?   # 可选；未指定时采用偏序的确定性拓扑序

ResourceRequest:                       # 自包含：时间后端不回读 CoreIR/PlacementPlan
  target: ExecutionTargetId
  work:   { flops, special_ops, reduction_ops }   # 分 model / executed 两套
  traffic:{ memory, transport }
  pricing:PricingDescriptor            # 含 compute/accum dtype、cost family、基础签名
  provenance: 逐量携带（见第 2 章）

8.4 数据流与逻辑流程

  1. 按调度（1F1B / 交错虚拟流水）展开 (stage × microbatch × 节点)；重算节点已在 S3 入图，此处无特例。
  2. 为每个值实例分配 StorageInstanceId：alias 映射到根存储（零分配）， inplace 在变更点结束旧值的生命周期，重算再物化使用新的 epoch。
  3. 根据 S3 的释放点偏序生成 Retire/Free；被保存的值通过 Pin 延长生命周期，不改变其字节（需要独立字节的一律建成内部保存值）。
  4. 为每个 BufferContract 按放置结果解析本地字节，并物化为半开区间的申请/释放对。
  5. 生成资源请求：每个量均携带 provenance，measured 项在此绑定标定 key。
  6. 联合预检：所选后端需要的能力是否完整、事件是否不重不漏、偏序是否无环。未通过时不产出任何部分计划。

Chapter 9S6 后端与 S7 报告

9.1 显存后端

显存后端只消费 MemoryEventView。核心状态是「当前存活的物理实例集合」。它按事件推进，并依据内存池与对齐规则模拟申请和释放，给出已分配/已保留峰值、OOM 判定及首次失败证据。结束前执行终审：不得残留未释放的非持久实例，也不得存在尚未完成 lowering 的高层事件。

9.2 时间后端

时间后端只消费 ResourceRequest 与硬件/profile 快照。两级离散事件仿真保持不变（段内多流 → 全局调度）。定价采用分级回退链：命中兼容实测 → 形状/类型插值 → 已标定族模型 → 理论 roofline；每一级都记录 provenance 与 confidence，参数不完整时阻断，绝不静默降级为零成本或纯带宽模型。

9.3 报告

不变量

两个后端不共同构造报告，由汇总器聚合。报告必须分别统计三类 provenance 的覆盖率，并把 assumed 项的依据与偏差方向逐条列出。不允许把未覆盖项藏起来。

Chapter 10阻断与用户闭环

10.1 阻断范围（相较 v1 进一步明确）

情形处理为什么
未注册 Op阻断 + 生成骨架 语义未知时，任何估算都缺乏可验证依据；这种情况通常只在新增 kernel 时出现
已注册，含 measured 量允许执行 + 报告标注 标定值是已声明的实测事实，而非猜测
已注册，含 assumed 量允许执行 + 报告标注依据与方向 否则第 2 章定义的第三种状态无法得到表达，稀疏模型也无法执行
形状/类型无法求解阻断 source_derived 缺失即不可判定
为什么必须区分未注册与已注册的不确定量

如果将两者统一归入「不完整就阻断」，会产生两种结果：要么 assumed 无法表达，要么为了让仿真继续执行而将 assumed 伪装成 source_derived。后一种结果不可接受。

10.2 闭环流程

  1. 发现未绑定调用 → 阻断，并输出：符号、各输入的形状与类型、赋值目标、两个注册域的查找结果。
  2. 生成骨架：只填写可从调用证明的信息（selector、输入、attrs），其余字段全部保留 REQUIRED 占位。
  3. 用户补充完整 → 校验 → 解释（打印该 Op 展开后七个方面的完整语义，供人工复核）。
  4. 快照 digest 更新 → 相关缓存失效 → 重新编译 → 联合预检 → 开始仿真。

骨架里不含源码文件与行号——那些只出现在诊断输出，避免用户配置与源码位置耦合。

Chapter 11验收与迁移

11.1 验收基准必须来自真机

必须避免的方法论错误

迁移期间进行新旧双跑是必要的，但不能用旧路径判断正确性。将旧路径作为验收基准，等于把旧路径的已知偏差编码成新系统的验收标准。

一个仿真器的正确性定义只能来自被仿真的对象，不能来自它的前一版。双跑的正确用途是变更归因（哪些数值发生变化、为什么变化），正确性判定必须以真机实测为准。

门断言性质
真机对照逐 stage 峰值、逐层驻留、step time 与实测比值；实测数据带指纹校验，不得编辑唯一正确性判据
结构不变量随层数、微批数按既定倍数变化的结构关系，必须由模型导出，而不是直接写入公式正确性
轴代入一致两个后端对同一符号形状和同一并行度求得的本地元素数与字节数必须一致防分歧
provenance 闭合报告里每个字节可归到三类之一；assumed 项均有依据诚实性
阻断有效性参数化删除任一必填字段 → 必须阻断；显式空值 ≠ 缺失安全性
后端隔离两后端双向 import 禁令；后端不读源码/配置/注册表解耦
新旧双跑逐项分析差异原因，已知设计修正列入可接受差异（accepted delta）归因，非判据

11.2 迁移策略

不采用全量重写（数值变化无法归因），也不保留长期双轨（两套事实源必然产生漂移）。方案采用适配层 + 按算子族收编 + 双跑归因；每完成一个算子族的迁移，即删除对应的旧分支。

阶段内容该阶段的门
1语义基础设施：类型系统、组合子库、DSL 编译器、三个注册域加载期阻断用例全部通过
2适配层：将现有语义表转换为新的描述格式，并验证可保持不变的数值；由缺失字段或默认零值产生的结果一律标记为 legacy 假设，未经显式收编不得通过完整性门禁真机对照结果不劣化
3按族收编：视图/类型转换/比较 → 逐元素/归一化 → 矩乘 → 注意力 → MoE → 集合通信 → 融合每族收编后真机对照 + 双跑归因
4CoreIR + BackwardIR + 两个计划层不变量校验 + 轴代入一致门
5后端切换：显存后端改为使用事件视图，时间后端通过适配层复用现有两级仿真真机对照成为权威判据
6开放用户通道：注册、校验、解释、骨架生成闭环用例全部通过
7收口：删除旧分支，只保留兼容 API所有门禁均通过

11.3 实施前必须量化起点差距

诚实边界

「可执行 IR 中不存在 opaque 节点」是目标态的不变量，并非当前状态。启动阶段 2 之前，必须先量化并公布起点差距：当前抽取链上有多少调用仍无法绑定语义、级联失败的根因集中在哪些位置，以及哪些量在原理上无法从源码获得（例如，融合 kernel 自身输出的形状位于编译产物中，而不在源码中）。如果不先量化，何时达到完成标准将无法判断。

12.1 决策记录

#决策关键理由

12.3 诚实边界

本设计的能力边界
  • 融合 kernel 自身输出的保存集：末轴位于编译产物中，而不在源码中。声明通道可以承载该信息；若未提供声明，则标记为 Unknown，并停止给出数值，禁止猜测。
  • 数据依赖量的精确值：MoE 实际负载只能通过 assumed 描述。报告可以说明偏差方向与依据，但不能把它变成精确值。
  • 验证反馈周期：清晰分层的固有代价是，必须等待整条链完成后，才能得到第一个可与现实对照的数值。适配层与按族收编只能缩短这一周期，无法彻底消除——因此阶段 2 的门禁必须使用真机，而非旧路径。
  • 覆盖面：目标态不承诺一次覆盖所有模型族；未覆盖的层类型必须显式阻断，不生成空层结果。

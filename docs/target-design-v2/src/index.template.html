Chapter 0产品契约与非目标

0.1 本方案回答什么

输入模型源码快照、模型规格、当前 DP/TP/PP/CP/EP 配置、逐 rank 逻辑上下文、microbatch、 重计算与分布式优化器配置，以及目标硬件、显式 rank-device 部署、用户采集的计算算子成本数据、 stream/cost policy 和通信公式快照，本工具回答：

  • 按 tensor/storage 的显式申请和释放生命周期，预测每卡已分配内存峰值、峰值事件与构成；
  • 按正确依赖的执行事件 DAG、stream、P2P/集合通信关系，预测单步时间和关键路径；
  • 改变并行度、microbatch、重计算、分桶或预取后，内存和时间预测如何变化；
  • 哪些语义来自源码、派生规则、标定或工程假设，以及当前覆盖和未建模项。
核心契约：每个配置产生两个显式状态的 BackendResult，分别承载 MemoryEstimate 和 StepTimeEstimate。二者是可复现的工程点预测，不是数学证明。 数值必须与 evidence、coverage、assumptions、model_digest 和 simulation_digest 一起解释。

0.2 明确非目标

非目标本方案的处理原因

allocator reserved 与外部碎片只计算 logical allocated peak不把 tensor 生命周期与 allocator 池策略混为一体

0.3 如何阅读预测值

value 表示“按当前结构、语义规则、成本模型和配置仿真得到的预测”； evidence 解释每个量从哪里来；coverage 解释模型覆盖面；assumptions 列出为了完成预测而采用的工程规则。 覆盖率高不自动等于误差小，实测成本也不自动证明依赖与调度正确。

产品承诺的边界

相同生产输入摘要必须得到逐事件一致的结果；缺少必需语义时明确阻断受影响后端； 有对照数据时报告误差，没有对照数据时报告“未评估真机误差”，但不改变预测路径。

比较边界：memory 与 time 都不跨不同 logical-rank 集合猜测 rank 对齐；rank 集合不同即为 Incomparable，完整判定见 10.5 节。

Chapter 1总体架构与分层

1.1 权威生产数据流

RankCodeIR(P,r) 直接对应当前源码在当前配置、当前 logical rank 下可见的结构； 顶层 CodeIR(P) 是规范 rank 顺序的有序映射，不是一张带 rank 备择 guard 的母图。 RuntimeEventPlan 实例化一次训练 step 的 forward、backward、optimizer、recompute、 P2P/collective、microbatch 与 pipeline 事件。SimulationPlanCore 只绑定两侧共享的物理事实； memory/time projection 再各自绑定 storage/workspace 或 duration/通信路径。两个 candidate 先绑定到同一 request/config evaluation identity，在一个 ProjectionBundleAuthority 上联合执行 projection clauses，把全部 InputBlocker 先按 affected_backends 做 scope 闭包，然后才同时派生两侧 Ready、Blocked 或 NotRequested。backend value、最终三态结果与可选 comparison 也各有绑定当前 subject 的 seal，任何 candidate 在对应 seal 前都不可外泄。 因此缺 compute 测量不会妨碍构造合法的 memory view。不建立共享资源竞争；两个后端只读各自的自包含视图。

1.3 全局不变量

  1. 当前源码为权威：每个配置、每个 logical rank 从同一源码快照按 rank context 重新求值；不存在被特殊配置或 rank 裁剪后的唯一母图。
  2. CodeIR 不可变：创建后不在原图上增加、删除、替换或失活节点。
  3. 事件引用结构：重复执行通过新事件引用同一 code_node_id 表达。
  4. 硬件晚绑定：代码结构不读取容量、带宽、拓扑或 allocator 常量。
  5. 逐面证据：shape、alias、effect、duration 等分别记录质量，不用单一算子置信标签覆盖全部语义。
  6. 测试链隔离：真实运行对照可以阻止发布，但不参与生产数值计算。
  7. 双向完整：独立句法 obligation pass 枚举每个候选调用 occurrence，guard 作为分支证据；调用与训练 event obligation 各有一个显式 disposition，生成的每个节点和事件也各有一个反向授权。
  8. 确定性：相同生产摘要、逻辑 kernel 顺序和通信进展规则产生逐事件相同的结果。

1.4 输出不变量

  • 内存以每 rank peak_allocated_bytes 有序映射为权威结果，并附规范派生的 cluster max、峰值事件、timeline 与 storage 构成。
  • 时间以 predicted_step_time 标量呈现，并附关键路径、逐 stream/stage 忙碌区间、模型内 overlap、pipeline idle 与 service 构成。
  • 严格同口径才可比较：对每个 metric，除显式 comparison axes 外，模型/工作负载、硬件、相关 registry/cost dataset、fallback/assumption policy、实际解析结果和后端语义版本均相同才输出数值 delta。
  • 口径不同返回 Incomparable 与逐项 mismatch，不把模型变化解释为策略收益。

Coverage 是覆盖事实，不是置信概率。源码 obligation 的分母由当前源码、配置与 rank context 在生成 IR 之前独立枚举；event obligation 的分母由冻结训练语义规则枚举，二者不得从已生成节点反推。 必须满足 source_total = planned + residual + proven_not_executed 与 event_total = planned + blocked + not_applicable；每项恰落入一个桶。 100% op coverage 不能证明 stream、lifetime 或 collective 规则正确； 一个 duration 来自标定，也不能替代对 event DAG 的验证。报告不得自动生成没有统计依据的 confidence 百分比。

EvidenceTag 具有 basis-specific 必填约束：source 必须有 source_ref；measured/calibrated 必须有 ObservationRef、单位和适用域；modeled communication 必须有 CommunicationFormulaRef 与全部公式输入； assumed 必须有 AssumptionId。仅填写通用 rule_id 不能把证据升级为相应 quality。

成功与阻断语义

Ready 表示请求及所有引用快照均可规范序列化和内容寻址。 Blocked 仅表示调用者提供的输入或冻结事实不足，例如入口源码/依赖缺失、所请求的完整快照缺失， 或原始配置无法形成唯一正则形；它携带规范 BlockerRecord。缺少某个后端的单项 cost record 不阻断请求组装，而由该后端 projection 形成部分结果。对已经通过输入校验的数据，若 builder 产生 重复 ConfigRef、非规范顺序、互相矛盾的 payload/digest 或无法解释的分支，则返回 InternalContractViolation，不得伪装成输入 blocker。

不变量

  • 每个 ConfigRef 恰对应一个 CanonicalConfigEvaluationInput，其 normalized P、rank context、scenario 与 deployment 互相一致；
  • snapshot 和 map 均按规范 key 顺序序列化；所有派生 digest 只排除自身字段并可由 payload 重算；

  • 相同规范输入产生字节相同的 RequestSnapshot；TraceFixture、holdout 和请求时 profiler 不进入生产 payload 或 digest；
  • requested_backends 只决定后端是否请求，不改变源码、配置或共享结构语义；RequestSnapshot.request_digest 覆盖完整 tagged map，但每个 NotRequested arm 都是无 payload、无 digest 的闭合空分支；

Chapter 4逐 rank CodeIR(P) 与源码求值

4.1 PySub 边界

源码求值器解析受支持 Python 子集 PySub：模块/函数调用、属性访问、局部赋值、容器、 配置 guard、有限循环展开与可解析 import。它不执行目标训练，也不需要导入会启动设备或分布式环境的模块。 所有解析结果保留 source span、调用目标证据、rank context 和当前配置分支。求值世界由 SourceSnapshot、 CompileEnvFacts 与冻结 registry 封闭；未快照的 monkey patch、hook、descriptor 或 tensor dispatch 若可能改变调用图，必须产生 residual 并以 BLK-SOURCE 阻断，不能按静态目标静默继续。 任何当前可达但落在 PySub 之外的 executable construct 也必须生成带 backend scope 的 ResidualSite； 句法 obligation pass 不能因为“不支持”而跳过其内部候选调用。

4.2 每个配置逐 logical rank 直接构图

给定当前 P，求值器按规范 logical-rank 全序逐 rank 求值： RankCodeIR(P,r) = evaluate(SourceSnapshot, ModelSpec, P, RankEvalContext(r), ExecutionScenario.code_input_shape_dtype_bindings, CompileEnvFacts)。 顶层 CodeIR(P) 是这些 rank-local IR 的有序映射。TP、MoE、PP stage/chunk 分配、重计算开关 或显式 fused module 若改变源码分支，就由当前 P/rank 在源码中选择对应分支。仿真器不先构造一个特殊 配置或代表 rank 的图，再手工恢复其他分支。

模块契约 · 逐 rank CodeIR 构建

职责边界

本模块逐 logical rank 求值固定源码，并把源码可见调用、value/storage identity、数据/控制边与 source obligation disposition 汇总为不可变 CodeIR。逐 rank ownership 只消费 Trainer 配置规范化器写入 LogicalRankContext.layer_and_expert_ownership 的 stage/layer/expert 分配， 求值器不得另行猜测或平均分配。CodeIR 不读取 HardwareProfile、 TimeCostPolicy、duration、workspace、physical stream 或 allocator；microbatch occurrence identity 不复制进 CodeIR， 只在后续 RuntimeEventPlan 实例化。完整 NormalizedParallelConfig 仍是 evaluate_source 输入， 其中 shape/guard 相关 batching 字段可以改变 CodeIR；禁止复制的只是运行时 occurrence identity。

成功与阻断语义

rank-local Ready 表示可形成自包含 RankCodeIR；可定位的 residual 仍以 residual_blocker_records 保留，并在 assemble 时进入 CodeIR.blocker_index。 Ready 与 Blocked 两个分支都携带并满足 result.rank_build_input_digest == rank_input.rank_build_input_digest；跨输入重贴任一分支属于 InternalContractViolation。若至少一个 rank Blocked，assemble 返回全部 Ready residual 与 Blocked blockers 的规范 union，不能因顶层无法形成 CodeIR 而丢掉其他 rank 的已知根因。 Blocked 仅表示源码、shape/dtype binding 或冻结 Structure registry 事实不足到无法构造一致的 rank artifact。已验证输入之后若 builder 产生重复 local ID、无定义 TensorValue、悬空边、漏 rank、 obligation 多重 disposition 或 payload/digest 自相矛盾，则是 InternalContractViolation， 不得降格为 BLK-SOURCE。

不变量

  • LogicalRankContextSet 中每个 rank 恰调用一次 evaluate_source，assemble 的 key 集合和规范顺序与该集合完全相等；
  • 每个候选调用和 guard obligation 恰有 CodeNode、ResidualSite 或 ProvenNotExecuted 之一的规范 disposition，且每个 CodeNode 有唯一反向授权；
  • 每个 TensorValue 有唯一 definition；每个 storage-bearing tensor 由唯一 TensorStorageRelation 指向一个存在的 allocation root；DataEdge、ControlEdge 和 storage 引用均 rank-local；
  • 相同 RankCodeIRBuildInput 产生字节相同结果，硬件和时间事实不能改变它；microbatch occurrence identity 不复制进 CodeIR，但 shape/guard 相关 batching 字段可以改变 CodeIR。

6.4 Replay 与最小顺序规则

can_replay(node, context) :=
  effects.replayable
  and rng_state_contract_satisfied(node, context)
  and no_uncompensated_write_or_mutation(node, context)
  and collective_order_preserved(node, context)

event_effect(e) := RuntimeEventPlan.resolved_event_semantics[e].effect_summary

write_set(e) := event_effect(e).writes
                ∪ canonical_state_refs(event_effect(e).mutates)
                ∪ rng_write_refs(event_effect(e).rng)
                ∪ host_global_write_ref_if_any(event_effect(e).host_side_effect)
read_set(e)  := event_effect(e).reads ∪ rng_read_refs(event_effect(e).rng)

conflict(a, b) :=
  write_set(a) intersects (read_set(b) union write_set(b))
  or write_set(b) intersects (read_set(a) union write_set(a))

overlap_permitted(a, b) :=
  not conflict(a, b)
  and disjoint(event_effect(a).nonoverlap_domains,
               event_effect(b).nonoverlap_domains)

phase_order :=
  forward < backward < recompute < optimizer < communication
optional_virtual_chunk_order := None < Some(integer ascending)

canonical_instance_order_key(e) :=
  (logical_rank, logical_schedule_slot, phase,
   microbatch, virtual_chunk, repeat_ordinal, event_id)

base_event_graph :=
  frozen(data edges ∪ required source/control edges
         ∪ ScheduleConstraintEdges)
require acyclic(base_event_graph)

canonical_base_order :=
  stable_topological_order(base_event_graph,
                           tie=canonical_instance_order_key)

for each unordered event pair in canonical pair-key order:
  if not overlap_permitted(a, b):
    orient exactly one required effect edge from the earlier event
    to the later event in canonical_base_order

RuntimeEventPlan.dependencies :=
  canonicalize(base_event_graph.edges ∪ required_effect_edges)
require acyclic(RuntimeEventPlan.dependencies)

该规则只解决执行先后，不建复杂 effect algebra，也不引入资源竞争。语义不允许 overlap 不是报告标签： 在生成只读视图前必须由 base graph 的已有 reachability 或带 reason/witness 的 EventEdge 物化。所有 pair 都沿同一个 base DAG 的规范稳定拓扑全序定向，因此新增边不可能反向穿越 base path，也不因 pair 遍历顺序 形成环。必须遵守的源码顺序先物化为 control edge；“source order”不是后续实现自行解释的隐式比较器。 tuple 中枚举、None 与整数顺序按上式固定，EventId 按规范字节序。若 base graph 本身成环、StateRef 无法归一化或 RNG save/restore 不闭合，以 BLK-EFFECT 阻断。 本设计不执行算子融合，因此 EffectSummary 不承担融合合法性证明。

7.2 Forward 与 backward

forward 事件按每个 RankCodeIR 的数据、control 与 effect-derived 依赖，针对每个 microbatch occurrence 完整实例化。backward 由注册的 autograd 语义生成，保留对应 forward origin、saved TensorInstance、gradient producer/consumer、累加与参数更新关系。生产门同时检查正向 obligation 没有 漏/多事件，以及每个要求梯度的正向实例均有闭合 backward relation；未知 autograd、saved-tensor 或 grad-accumulation 规则以 BLK-EVENT-SEMANTICS 阻断两个后端，不修改 forward CodeIR。 同 origin 或同 microbatch 存在重复实例时也必须由显式 AutogradLink 唯一配对，不能按位置猜测。

7.4 Optimizer 与通信

optimizer、梯度累加、参数/状态更新和分布式优化器事件由当前 OptimizerSpec、 ParallelSpec 与注册运行时语义实例化。源码显式 collective 直接引用其 CodeNode； 框架派生 collective 使用 RuntimeRuleInvocationRef，并保留 group、rank、sequence、bytes 和 correlation id。 PP activation/gradient 与 CP ring 的点对点通信必须生成显式 send/recv endpoint 与 P2PIntent， 不得只用普通跨 rank dependency 暗示消息。

7.5 Microbatch 与 pipeline

每个 microbatch、pipeline stage、virtual chunk 和 phase 生成独立事件实例。 LogicalScheduleSpec 中任何必须约束实际发射/完成先后的条件，都必须由版本化 lowering 生成 ScheduleConstraintEdge 并进入 RuntimeEventPlan.dependencies；跨 stream 约束不能只写进 total order。 logical_kernel_order 只是内存重放和确定性 tie-break 的全序，不能替代执行依赖。 逻辑 schedule 不指定物理 stream 或 duration。 warmup、steady、cooldown 和 bubble 由后续 DES 在完整事件图上产生。

7.6 禁止的结构变化

训练事件展开不得修改 CodeIR 的 op 集合、边、shape、dtype 或 storage relation。 源码中显式 fused op 始终保留一个 origin；源码中的普通多 op 始终保留多个 origin。 任何内部 kernel 选择只进入成本和 workspace 证据。

  Allocate(s, b) => assert s not live; live_allocated += b;
                    live_by_category[category(s)] += b
  Bind(t, s)     => bytes unchanged
  Use(t, op)     => bytes unchanged
  Free(s)        => assert s live; live_allocated -= bytes(s);
                    live_by_category[category(s)] -= bytes(s)

  require for every anchor/category c:
    breakdown[c] == sum(bytes(s) for live s where category(s) == c)
  require sum(breakdown.values) == live_allocated

  peak_allocated_bytes[r] := max_anchor live_allocated(anchor)
  peak_anchor[r] := first in (INITIAL_STATE < canonical MemoryEventId)
                    among argmax live_allocated(anchor)

cluster_max_rank := min_LogicalRank(argmax peak_allocated_bytes[r])
cluster_max_peak_allocated_bytes := peak_allocated_bytes[cluster_max_rank]

每个 StorageInstance 恰好来自 initial live-in 或一次 Allocate，二者互斥；非 persistent instance 恰好一次 Free，初态也可成为峰值 anchor。 alias/view/in-place 只 Bind 到已有 storage，不重复计数。后端不模拟 pool、split、merge、coalesce、 reserved、外部碎片、容量检查或首次分配失败。

build_backend_result_candidate(source_authority):
  bundle_authority := source_authority.projection_bundle_authority
  backend := source_authority.backend
  projection_result := source_authority.source_projection_result
  if projection_result is NotRequested:
    value_authority := BackendValueGateAuthority(
      source_authority, ValueSubjectNotRequested)
    pre_seal_ledger := run_backend_value_gate_stage(value_authority)
    require every new backend-value record is evidenced NotApplicable

      value_authority, ProposedNotRequested, pre_seal_ledger)
  if projection_result is Blocked { blockers }:
    value_authority := BackendValueGateAuthority(
      source_authority, ValueSubjectBlocked)
    pre_seal_ledger := run_backend_value_gate_stage(value_authority)
    require every new backend-value record is evidenced NotApplicable
    return assemble_seal_pair(
      value_authority,
      ProposedBlocked {
        blockers=blockers,
        diagnostics=derive_diagnostics(blockers) },
      pre_seal_ledger)

  ready_view := projection_result.view
  execution :=
    if backend == memory: run_memory_backend(ready_view)
    if backend == time: run_time_backend(ready_view)

    return violation; no candidate/result

    build_estimate_candidate(ready_view, value, witness)
  value_authority := BackendValueGateAuthority(
    source_authority, ValueSubjectOk { estimate_candidate })

    value_gate_authority_digest, estimate_candidate.value and witness
  if any applicable new backend-value clause is Fail:
    return InternalViolation { violation: canonical_internal_violation_union(all_internal_violations) }; no candidate/result

    value_authority, ProposedOk { estimate_candidate },
    pre_seal_ledger)

成功与阻断语义

每个请求 metric 恰产生 ComparableDelta、Incomparable、 Unavailable 或 NotRequested。只有左右同 metric 均为 Ok 且 basis 字节相同才可 Comparable；左 baseline 为零时 relative 分支必须是 UndefinedZeroBaseline，absolute delta 仍按 right-left 计算。basis 不同必须输出逐路径 BasisMismatch；单侧不可用必须携带左右状态和诊断； 两侧都未请求才是 NotRequested。authority、candidate 或 G-REP2 失败是 InternalContractViolation，不得伪装成 backend blocker。

不变量

  • left/right config_ref 必须等于 ComparisonRequest，EvaluationInstanceIdentity 必须从 same RequestSnapshot 逐臂重算；每个 artifact 的 request_digest、evaluation_instance_digest 和 backend 与臂身份逐字相等；
  • 每臂 memory/time artifact 的 nested ProjectionBundleAuthority 字节相同，且两臂都绑定 source 的 ProductionValidationContext 与 GateManifest；A/B artifact 不得交换；
  • 令 snapshot := request.canonical_production_evaluation_inputs.common_inputs.comparison_schema_snapshot；comparison axes 必须绑定其 comparison_schema_snapshot_digest，declared_paths 必须属于 allowed_axis_paths，且 derivation_closure == derive_closure(snapshot, declared_paths)。closure 只由 snapshot 的 root schema 与 cross-field rules 推导，调用者不能增加路径；
  • canonical_comparison_basis_pairs 精确覆盖 requested metrics；derive_comparison_basis_pair recomputes 当前 RequestSnapshot 中的 schema snapshot、declared paths 与完整 closure 后，才从完整 CanonicalConfigEvaluationInput mask；G-REP2 recomputes 同一等式并逐 metric 对照当前 authority/candidate，不能信任调用方携带的 closure 或旧 basis pair；
  • config identity、左右 basis 与同 metric 状态分别判定；registry/calibration/fallback/assumption、measurement protocol、numeric/backend semantics 或未声明扩展字段不同均形成 BasisMismatch，不能伪装成策略收益；
  • CoverageDelta 只在 ComparableDelta 内由两侧 Estimate.coverage 规范派生；任何非 ComparableDelta 分支都不携带数值 delta。

negative fixture: inject other_config_indexed_production_inputs.x into derivation closure；验证器必须拒绝该调用方扩展，且若左右该字段不同， BasisMismatch.schema_path == other_config_indexed_production_inputs.x，不能因伪造 closure 而被 mask。

    comparison_runtime_authority, comparison_base,
    comparison_domain.new_execution_invocations)

    gate_evaluation_context_digest(comparison_gate_subject) and validates the current authority/candidate

          stage_evaluation_context_digests ==

          applicability, dependency and aggregate-outcome equations all hold

           no ComparisonResult/cache/report

    seal_authority, comparison_gate_ledger, candidate.value)

Chapter 11阻断、回退与诊断

11.1 阻断分类

BlockerCode 是分类，BlockerInstanceId 是一次根因实例；二者不得复用。 下表“范围”是规范 BlockerScopePolicy：固定“两侧/内存侧/时间侧”的 code 必须精确得到该集合； “受影响侧”必须由 failed_invariant_ref 的声明式 face dependency 求值；communication buffer identity/lifetime 是否受影响也由 intent buffer contract 求值。每个 BlockerRecord 必须满足 affected_backends == BlockerScopePolicy.resolve(blocker_code, stage, failed_invariant_ref, diagnostic_seed)， 不得由调用方自由填写。同一 EvaluationInstanceIdentity 的两侧 projection gate 必须全部完成后， 先对所有 InputBlocker occurrence 做全局规范并集，再按 affected_backends 投影到 memory/time；全局闭包前 任一侧都不得产生 source authority 或进入 backend seal。另有一条阶段不变量：若 failed invariant 使 RuntimeBuildResult、CoreBuildResult 或 shared G-IR invocation 无法为 Ready/Pass， BlockerScopePolicy.resolve(...) 必须精确返回 {memory,time}。“受影响侧”的单侧 scope 只能在 shared RuntimeEventPlan/Core 仍然 Ready 后由对应 candidate 或 view gate 产生，不得用单侧 blocker 摧毁共享 artifact。

fallback 必须是冻结 registry/policy 的一部分。compute 只能使用用户 CalibrationSet 中与 MeasurementKey 精确相等且唯一的 active record；禁止插值、roofline/FLOPs/零值回退。 通信只能使用 CommunicationModelSnapshot 中按冻结 selector 唯一选出的具名理论公式与 route： 0 个候选以 BLK-MISSING-TIME 阻断，多个同等最优候选以 BLK-AMBIGUOUS-COST 阻断。 内存侧每个 storage/workspace 只能使用唯一 StorageBinding/WorkspaceBinding；普通 storage 仅对明确声明为 新建、dense、无 padding 的对象使用 shape × dtype，再按显式 alignment 等式求 allocated bytes； view/layout-dependent storage 禁止该 fallback，algorithm-dependent 通信内部 scratch 禁止猜测。 未知 workspace、effect、persistent live-in 或 lifecycle 不能填零。每次 resolved fallback 更新 evidence、 coverage、assumptions 和 simulation_digest。

成功与阻断语义

本轮 domain 包含 current root stage 的全部规范 backend/branch sibling invocation；适用新 invocation 的 dependency transitive closure 只在不可覆写的 base ledger 中验证且必须全部为 Pass，不重跑也不重贴。NotApplicable 只表达非适用 sibling 自身，绝不授权任何适用节点；typed coordinates 只决定新 invocation 的 applicability。 适用 invocation 的每个 manifest clause 恰执行一次；不适用 invocation 仍保留 带 predicate 证据的 NotApplicable。所有 clause 执行完成后，projection 侧先形成 canonical union of every InputBlocker failure occurrence， 再与 runtime/core/construction blockers 作全量规范并集并按 BlockerScopePolicySnapshot 投影后端；禁止 early return 丢失根因。只要任一 failed clause 的权威 disposition 是 InternalViolation，InternalViolation takes priority， 终止当前 request 并保留完整规范 violation set；它 must not be converted to InputBlocker、Blocked 结果或诊断。

不变量

  • manifest entry map key、entry.invocation_id 与 GateExecutionRecord invocation_id 逐字相等；每个 exact current-stage invocation domain 的 records key 集无增漏，conditional domain 由当前 request/backend/branch/stage 和 dependency DAG 唯一派生；
  • 每个适用 invocation 的 clause_outcomes key 集精确等于 manifest clauses；必须满足 clause_record.clause_id == clause_key == clause.clause_id，predicate digest、failed_clause_ids 与 Pass/Fail 聚合式逐项闭合；
  • ClauseFail 不携带 disposition；每个 failure occurrence 逐 clause 读取 effective_failure_disposition，execution record 不得覆写或合并不同 clause 的 disposition；
  • 必须满足 manifest.blocker_scope_policy_digest == authority.blocker_scope_policy.blocker_scope_policy_digest；每个 InputBlocker disposition 的 ScopePolicyRef digest 等于该值，并解析到 unique rule selected by scope_policy_ref.rule_id，且 selected_rule.blocker_code == disposition.blocker_code；
  • 每个 GateClause 的 coverage_requirement: ClauseCoverageRequirement 要求正例与负边界例并与 normative_clause_refs 一一全覆盖；该生产 schema contains no fixture identifiers，具体绑定只在离线 FixtureSet；
  • authority 的 subject_digest、manifest subject/runner 与 ProductionValidationContext/runner 逐字相等；每条新增记录必须满足 gate_record.evaluation_input_digest == gate_evaluation_context_digest(subject) 与 clause_record.evaluation_input_digest == gate_evaluation_context_digest(subject)，且等于 current_stage_contexts；base 记录继续绑定其原 stage context；
  • ledger extension 逐字保留 base 的 manifest/subject/runner、covered stages、stage contexts 与 records；base records and stage contexts are copied byte-for-byte；只允许追加 disjoint current stage/domain，no required prefix invocation is executed or pasted again；任何覆盖、删除、重贴，或适用 invocation 的 dependency closure 中存在非 Pass 记录，均为 InternalContractViolation。

合法闭包例必须逐字证明：legal ResultSealSubject context == hash(backend_seal_authority_digest, backend_result_candidate_digest)， 以及 legal ComparisonGateSubject context == hash(comparison_seal_authority_digest, comparison_result_candidate_digest)； 不得另建 tagged-payload digest 或只覆盖 seal authority 而漏 candidate。

发布 verifier 的边界负例必须包含 negative fixture: policy digest mismatch 和 negative fixture: dangling scope rule；两者均返回 InternalContractViolation，不能继续 scope resolution。

negative fixture: runtime manifest uses wrong predicate runner 必须在执行 predicate 前失败；即使 manifest、 runner 与 request 各自 digest 自洽，只要 runner payload 不等于 request-owned GateRunnerSnapshot，或任一 applicability/clause predicate digest 不等于该 runner map 的精确 ref 项，就不得构造 runtime GateEvaluationAuthority。

invocation domain 负例必须包含 negative fixture: invocation subset、 negative fixture: invocation superset 与 negative fixture: wrong stage context； 还必须包含 negative fixture: wrong subject arm。这些 fixture 使用 literal hand-derived expected domains， 测试 reference derivation must not call expected_invocation_domain 或任何被测 helper；subset、superset、错 stage/context 或把 memory authority 塞入 time subject tag 的任一情况，都在执行 predicate 前返回 InternalContractViolation。

negative fixture: memory-only request retains time view sibling as NotApplicable，且 negative fixture: ProposedOk retains ProposedBlocked and ProposedNotRequested siblings as NotApplicable； 删除这些 current-stage sibling 或把它们误判为 applicable 均为 InternalContractViolation。

negative fixture: applicable invocation depends on NotApplicable sibling 必须失败：即使该 sibling 的 NotApplicable 记录与 authority 一致，它也只能证明 sibling 自身不适用，不能满足适用 invocation 的 depends_on。

negative fixture: memory ProposedOk prefix keeps G-MEM5/6 value context V while result seal stage uses R only for new execution： 令 V := value_gate_authority_digest、R := hash(backend_seal_authority_digest, backend_result_candidate_digest)； 必须满足 base.stage_evaluation_context_digests[backend_value_postcondition] == V 且 expected.current_stage_contexts[result_seal_postcondition] == R。G-MEM5/6 records and value-stage context remain byte-identical V， R appears only at result_seal_postcondition；未请求或非选 ProposedBlocked/ProposedNotRequested sibling 仍是 NotApplicable。

模块契约 · 离线 Conformance 与发布判定

职责边界

本模块只在测试目录或 CI 中，以冻结 fixture 对精确 content-addressed ProductionSubject 和 GateManifest 做独立验证并给出发布判定。fixture、finding、report 与 release decision 全部 outside production digests and cache keys； 生产 API、仿真进程、comparison basis 和缓存查找不得读取它们。Conformance verdict does not alter BackendResult， 也不能补齐、改写或重新封装任何生产结果。

run_conformance 先复算全部输入摘要，执行完整 binding domain，并要求 ledger 的 expected domain、 execution records、finding 与 coverage gap 守恒。runner crash, schema failure, digest failure or conservation failure 均返回单一 InternalContractViolation，且不产生 report 或 seal。只有完整合法执行才构造 report、runner attestation、 ledger 与 ConformanceSealArtifact。每条记录必须满足 record.fixture_ref == record_key、 record.target_invocation_id == binding.target_invocation_id 与 record.target_clause_id == binding.target_clause_id，并复算 fixture/input/output/record digest。

runner attestation 的信任能力来自部署/verifier 持有、请求反序列化无法构造的 ConformanceTrustRootCapability， 不来自 invocation authority 或 runner 自报。authority 只持 trust-store/policy refs 与 digests；validator 先把它们与外部 root 的完整 payload/digest 逐字对照，再复算 store 的 key registry/snapshot digest 与 policy digest，并要求两者支持的 scheme 集合一致， 再按 policy 选择 key id 与 scheme，从 store 读取固定 trusted key material。签名消息逐字覆盖完整 measurement envelope digest、 executable artifact、key id、scheme、conformance invocation、observed output 与 verifier runner 七项摘要/标识。envelope 自身摘要覆盖 invocation、runner/executable、session/process/container identity、single-use verifier nonce、执行时间窗、实测 payload 与 measurer identity/freshness evidence；payload 摘要再与 policy expected 值比较，不能直接把 expected 值当测量值签名。 所有 binding 只能在由该 envelope 激活的同一调用域 session capability 下执行；attestation、ledger、report 与 seal 中的重复摘要必须逐字相等。

发布批准另由部署/verifier 持有、请求、fixture、ReleasePolicy、approval store 与 approval artifact 都无法构造的 ReleaseApprovalTrustRootCapability 授权。validator 在接触该 root 的公钥材料前，先完成 seal artifact 全部 nested digest、 批准 store 及其 ApprovedDigestSet values、ReleasePolicy、approval authority/artifact 和十字段 derived approved set 的重算；随后要求 root 固定的 ReleasePolicy 与 approval-store payload/digest 逐字相等，只允许 root-supported scheme，并仅从 root 的 trusted approver public-key registry 解析验签材料。批准签名消息覆盖 root 固定的 policy/store identity、key/scheme 与规范十字段 ApprovedDigestSet； policy 中的 key id 只是经外部 root 认证后的选择器，不能充当公钥或自证信任根。

成功与阻断语义

每个 manifest clause 必须同时有 positive fixture 与 negative-boundary fixture，并验证预期 failure disposition；只有 complete, valid execution 对全部已声明 binding 执行且守恒后，coverage gap 才使 verdict 为 insufficient 而不是 pass。结构/数值不符产生 fail 和逐 clause ConformanceFinding；缺独立证据产生 insufficient。release policy 对 pass/fail/insufficient 三态分别处理：fail 总是阻断精确 subject，pass 只有 approved == derive_approved_digest_set(artifact, policy)、全部十个字段逐字相等且外部 release trust root 验签有效才允许，insufficient 的 allow/block 必须由版本化 ReleasePolicy 明示，不能默认为 pass。

发布负例必须包含 negative fixture: no execution but forged all-pass、 negative fixture: forged runner attestation、negative fixture: forged ApprovedDigestSet 与 negative fixture: tampered execution record or observed output。前三者不能靠自填 digest 获得 capability， 后者不能在重算 record/global output 后保持 signature；均不得生成或放行 seal。runner crash 仍返回单一 ICV； insufficient 只允许在 authority、逐 binding execution、observed output、signature 与守恒全部合法完成后表达证据缺口。

negative fixture: valid signature plus failing observed output cannot be sealed with forged pass： 即使 runner signature 有效，validate_and_seal_conformance 仍内部重算 report，调用方无法提交或替换 verdict。

negative fixture: release approval wrong signature scheme 与 negative fixture: unsupported release approval signature scheme 必须在读取批准 verdict 前失败； authority 不能选择与 ReleasePolicy 不同或 verifier 不支持的 scheme。

release approval trust 负例还必须包含 negative fixture: release approval self-owned approver key、 negative fixture: release approval wrong store snapshot、 negative fixture: release approval unsupported signature scheme 与 negative fixture: release approval substituted policy；自带 key、非 root 固定 store、root 不支持的 scheme 或替换后的 policy 即使全部 caller-owned digest 与 signature 自洽，也必须在读取 verdict 前返回 InternalContractViolation。

runner attestation trust 负例必须包含 negative fixture: wrong runner attestation trust store、 negative fixture: unsupported runner attestation signature scheme、 negative fixture: tampered runner execution environment 与 negative fixture: runner self-owned attestation key；wrong store、unsupported scheme、被篡改 environment 或 runner 自带 key material 任一情况均在 report/seal 构造前返回 InternalContractViolation。

negative fixture: old invocation digest plus substituted policy or trust-store reference：validator 的首个动作必须 先复算 authority 的全部 nested input digest，再复算 invocation digest；替换 ValidationPolicy 或任一 trust-root ref 后沿用旧 digest 必定在读取 observed/ledger/attestation 或选择 key/scheme 前失败。外部 root payload 与 authority ref 不等、把 self-owned store 伪装成 root，或用 expected environment digest 代替 protected measurement 同样不得产生 report/seal。

negative fixture: replay valid measurement envelope from another execution session 必须因 session/process/container identity 不等或 single-use nonce 已消费而在任何 binding 执行前失败；即使 payload 与 expected environment 完全相同也不能复用。 negative fixture: change only measurer identity or freshness evidence while retaining old envelope digest 必须在 envelope 摘要复算或 measurer evidence 验证时失败；change only measurer_identity_and_freshness_evidence changes measured_execution_environment_digest， 因此 provenance/freshness 不是摘要外旁注。

不变量

  • report.production_subject 必须由 build artifact、evaluator/registry、production policy、backend semantics 四组 constituent 重算，report.subject_digest、manifest.subject_digest 与 approval.authority.approved.subject_digest 逐字相等；
  • fixture_set_digest、validation_policy_digest、gate_manifest_digest、verifier_runner_digest 必须分别由 invocation authority 的实际 FixtureSet、ValidationPolicy、GateManifest、VerifierRunner 重算并与 report/approval artifact 逐字相等；

  • MeasuredExecutionEnvironment 是由 protected measurer 发行、绑定精确 invocation/runner/executable/session/process/container/nonce/time window 的 envelope；其摘要覆盖 payload 与 measurer identity/freshness evidence，single-use nonce 只可原子消费一次，全部 fixture binding 只在同一 call-scoped session capability 下执行；

  • fixture lineage 与 calibration_train/holdout/生产请求全隔离；删除全部 fixture/report/release artifact 不改变任一生产摘要、cache key、BackendResult 或 ComparisonResult。

14.3 没有真实 trace 时

没有当前待预测运行的 raw trace 时，工具仍从 CodeIR、RuntimeEventPlan、HardwareProfile、 CalibrationSet 和 CommunicationModelSnapshot 生成 memory 与 time 预测；但时间侧仍要求用户预先采集、 冻结且 MeasurementKey 精确匹配的 compute duration records。 并把 source/runtime/cost/schedule 规则分别标为对应 evidence。没有调度级对照时， stream、overlap 和 collective schedule 的真实误差状态为“未评估”，而不是阻断或零误差。

14.4 Trace 与 CalibrationSet 的最终分界

TraceFixture 是固定独立测试样本，用于发现结构或调度偏差；CalibrationSet 是用户预采集后经过 规范化、版本化、域标注和独立质量验证的 compute 成本数据。生产 lookup 只使用 calibration_train 中 精确匹配且唯一的 active record；holdout 只评估采集/适用性误差，不参与 duration 定价。前者不能进入 生产请求或 cache lookup，后者必须进入相应 backend simulation digest。 把待预测运行的 raw trace 转换成即时标定输入不属于本方案。

外部信任根

sample_key、digest 与 lineage 只能证明规范内容的一致性，不能单独证明测量真实、未篡改、 train/holdout 真正独立或样本有代表性。需要更强保证时，采集器身份、原始 artifact、时间窗和硬件环境 必须由方案外的签名/attestation 信任根背书；没有该信任根时报告明确标为“用户提供的测量事实”。

14.5 最终能力边界

生产 evaluator 能力

给定当前源码、当前配置、完整 rank context/scenario 和必需语义，逐 rank 生成硬件无关且可追溯的 CodeIR，展开正反向、microbatch、P2P/collective 与 effect-order 完整的训练事件，绑定 exact 用户 compute 测量和通信公式后输出每卡预测 allocated peak、预测 step time、timeline、关键路径、构成、coverage、 assumptions 和严格同口径配置差分；结构不完整时明确阻断； 生产请求、仿真摘要与结果缓存均不接收 holdout 或 conformance fixture。

离线 validator 能力

独立消费 HoldoutEvaluationManifest 或 TraceFixture，追加采集适用性、IR/schedule conformance 与误差报告； 这些离线制品不改变生产 BackendResult，也不成为生产发布前提或比较口径。

为什么这一形态符合多维并行规划

TP/PP/DP/CP/EP、microbatch、重计算、分桶和预取首先改变逐 rank 源码分支、运行时事件、 storage 生命周期与通信 rendezvous。对每个配置、每个 rank 直接复刻代码结构，再以逻辑顺序重放内存、 以无 contention 的全局 progress DAG 求 makespan，使两个指标从已声明机制中产生；compute 实测是显式 成本输入，待预测 raw trace 不是隐式 oracle，未建模竞争则作为固定能力边界披露。

# AST 探针报告 —— PySub 可行性度量

> **目的**：把设计里三个"目前是推的、不是测的"数变成测量值，并回答一个前置问题——
> **「模型结构可以由偏求值器在一个封闭语法子集上对框架源码偏特化得到」这个假设，在真实框架上成不成立。**
>
> **方法**：纯静态 `ast` 解析，**不 import、不执行**被分析框架。
> 脚本与原始输出在同目录（`astprobe.py` / `run_all.py` / `summarize.py` / `probe2.py`，
> 结果 `summary.txt` / `detail.txt` / `*.json.gz`），可复算。

## 0. 口径与规模

两个框架都全量解析成功，**解析失败 0 个文件**。

| 口径 | mindformers | Megatron-LM |
|---|---|---|
| 全仓 | 1254 文件 / 288,101 行 / 9,611 函数 / 1,818 类 | 1243 / 423,037 / 14,062 / 2,084 |
| 框架层（去掉测试、脚本、示例） | 598 / 184,334 / 5,736 / 1,015 | 543 / 209,426 / 5,753 / 796 |
| **模型定义子图**（PE 实际要走的） | **279 / 73,678 / 2,144 / 466** | **159 / 76,862 / 1,959 / 317** |
| 从模型入口出发的 import 闭包 | 459 / 148,536 / 4,706 / 845 | 206 / 120,162 / 3,507 / 472 |

**模型定义子图约占全仓的 1/4**——这是 PE 的真实工作集，不是整个框架。

## 1. PySub 覆盖率曲线（本报告的头号结果）

问的是：**PySub 支持前 N 种最常见语法构件时，能被完整解析的函数占比是多少。**
种子集 = 30 个基本构件（赋值、算术、比较、`if`、`for`、`return`、属性访问、调用……）。

| 覆盖率 | mindformers（5,736 函数） | Megatron（5,753 函数） |
|---|---|---|
| 仅种子 30 | 32.6% | 30.9% |
| ≥ 50% | **N = 3** | N = 4 |
| ≥ 80% | **N = 12** | N ≈ 13 |
| ≥ 90% | **N = 36** | — |
| ≥ 95% | **N = 47** | — |
| ≥ 99% | **N = 53** | — |
| 100% | **N = 61** | — |

**两个框架的曲线形状几乎相同**——这是"框架无关"主张的第一条正面证据。

### 结论一：PySub 不小，但它是有界闭集

**约 61 个构件覆盖 100%，47 个覆盖 95%。** 前 12 个就买到 80%。
这不是"几个构件就够"，也不是"无穷多"——是一个**可枚举、可版本化的表**，
正是设计要求的形态。

### 结论二（更重要）：阻断项是**平凡构件**，不是动态特性

模型子图内的 **sole blocker**（该构件是某函数唯一超纲项）排行：

| 构件 | mindformers 函数数 |
|---|---|
| `unpack.assign_seq`（`a, b = f()`） | 182 |
| `decorator.func` | 164 |
| `ctl.raise` | 110 |
| `expr.IfExp`（三元） | 68 |
| `oop.super_call` | 47 |
| `arg.kwarg` | 26 |

**这六项没有一项对偏求值器是困难的。** 元组解包、装饰器、`raise`、三元、`super()`
都是纯语法糖或可静态解析的结构。

真正难的动态特性全在**长尾**：`dyn.eval` 2 个函数、`dyn.compile` 11、`dyn.locals` 2、
`def __getattr__` 3、`def __setattr__` 4、`importlib` 调用 4。

**一处需要注意**：`getattr` 涉及模型子图 91 个函数（4.2%），其中 **77 个是常量字符串**
（PE 可直接求值），**18 个是动态的**（真正需要阻断或声明）。`hasattr` 同型（67 / 60 常量）。

> **⇒ 对设计的第一条结论：源码偏特化这条路线在语法层面成立。**
> 代价是 PySub 要有约 60 条，而不是设计文中隐含的"一个小子集"。

## 2. import 期 monkey-patch 点 —— 两个框架差 33 倍

模块顶层对**已 import 模块或其属性**的赋值（这类点会让"源码即事实"失效）：

| | 框架层总数 | **对已 import 模块/名字的赋值** | 涉及文件 |
|---|---|---|---|
| mindformers | 37 | **1** | 1（`tools/logger.py`） |
| Megatron | 35 | **33** | 25 |

Megatron 的 33 处集中在 `core/fusions/*`、`core/inference/*`（Triton kernel 注册、
推理路径），**不在模型定义主路径上**。

> **⇒ 对设计的第二条结论：这是"框架无关"主张的第一个反证。**
> 同一条设计约束（`BLK-UNDECLAREDSTATE` 之外还需要处理 import 期改写）
> 在两个框架上的严重程度差 **33 倍**。方案必须把"import 期 monkey-patch 点清单"
> 做成**逐框架的事实源**，而不是一条通用假设。

## 3. `PolicyStateBinding` 的规模 —— 是闭集，且有一条判据被数据救了

| | 顶层绑定名字 | 可变（任一证据） | **强可变（`global` 重绑定）** | 全大写命名 | **全大写里实际可变的** |
|---|---|---|---|---|---|
| mindformers | 625 | 95 | **24** | 355 | 53（误判率 **14.9%**） |
| Megatron | 989 | 394 | **143** | 440 | 261（误判率 **59.3%**） |

强可变全局高度集中：mindformers 的 `parallel_core/inference/parallel_state.py` 占 8 条；
Megatron 的 `core/parallel_state.py` 占 **49 条**。

> **⇒ 对设计的第三条结论：`PolicyStateBinding` 是闭集，规模 24–143 条（强可变口径）**，
> 完全可枚举、可进 digest。判据 3（非普适性）不失守。

**并且数据直接支持了设计里一条曾被质疑的选择**：设计 §3.4 坚持
"可变性判据是**赋值/变异点**，不是命名约定"。若退化成"全大写 = 常量"这个常见启发式，
在 Megatron 上**误判率 59.3%**——440 个全大写名字里有 261 个实际可变。
**那会让一多半的策略状态源静默漏标。**

## 5. policy-tainted guard —— PGRO 的真实工作量

模型子图内共 **758** 个策略污染 guard（子图内 `If` 3,523 + `IfExp` 457，**占 19.0%**）；
框架层 1,429 个。

**按字段组**（可重复计）：

| 组 | 数 |
|---|---|
| **MoE** | **283** |
| 并行度 | 237 |
| 精度 | 102 |
| 融合 / 实现选择 | 73 |
| 重算 | 66 |
| 调度 | 35 |
| 分布式优化器 | 11 |

**按改写类别**（决定 PGRO 义务的形态）：

| 类别 | 数 | PGRO 含义 |
|---|---|---|
| **`call_set_changes`** | **421** | **两支的调用集合不同 ⇒ 这是 PGRO 义务的主体** |
| `assign_only` | 153 | 只改变量赋值，不改调用 ⇒ 多半可折叠 |
| `assign_only_with_call_delta` | 138 | 中间形态 |
| `same_calls_diff_args` | 46 | 同调用不同实参 ⇒ 通常是 `Π_extent` |

**嵌套深度**（决定 PE 分叉会不会指数爆炸）：

```
policy-guard 嵌套深度：  0 → 645    1 → 96    2 → 16    3 → 1
```

**85% 是零嵌套，最深 3。**

> **⇒ 对设计的第四条结论：PGRO 的工作量主体是 421 条"改变调用集合"的 guard**，
> 不是 758 条全部。且**分叉不会爆炸**——85% 零嵌套，这对 `BLK-FUEL` 是正面信号。

### 一条与设计假设不符的发现

**MoE 相关 guard（283）多于并行度（237）。** 设计的三类策略划分
（`Π_extent` 广延型 / `Π_impl` 实现型 / `Π_semantic` 改变数学）默认策略主要是并行度，
而实测最大的一组是 MoE。

问题在于 MoE 的高频字段——`moe_layer_freq`（27）、`moe_layer_pattern`（11）、
`moe_token_dispatcher_type`（14）、`moe_router_load_balancing_type`（10）——
**很多是改变结构或改变数学的，而不是广延型的**。按设计的判据它们属 `Π_semantic`，
处置是"**归 Model 变量、要 what-if 就编译两次**"。

> **⇒ `Π_semantic` 这一类比设计预想的重要得多**，而它恰好是**唯一没有 pass 能重建**的那一类。
> 这直接影响 what-if 的可用维度：MoE 的多数旋钮可能都不在 `sweep_dims` 里。

## 6. 对设计的四条直接结论（汇总）

| # | 问题 | 答案 |
|---|---|---|
| 1 | **PySub 要多大才够用** | **约 61 条覆盖 100%、47 条覆盖 95%、12 条覆盖 80%**。阻断项是元组解包/装饰器/`raise`/三元/`super()` 这类**平凡构件**，真正的动态特性（`eval`/`compile`/`__getattr__`）只影响个位数到十几个函数。**路线在语法层面成立。** |
| 2 | **`PolicyStateBinding` 是不是闭集** | **是**，24–143 条（强可变口径）。并且数据证明"可变性必须按赋值/变异点判、不能按命名判"——按命名判在 Megatron 上误判率 59.3%。 |
| 3 | **PGRO 工作量量级** | 模型子图 **758** 个策略 guard，其中**主体是 421 条改变调用集合的**。嵌套 85% 为零 ⇒ 分叉不爆炸。 |
| 4 | **有没有哪条假设被数据否掉** | **两条。**（a）"框架无关"——import 期 monkey-patch 在两个框架上差 33 倍，必须做成逐框架事实源；（b）"策略主要是并行度"——实测 MoE guard 最多，而 MoE 的多数字段落 `Π_semantic`，**那一类没有 pass 能重建**。 |

## 7. 本报告没测的

- 每层原子 op 数、每事件 `Q` 实例数——需要一份**真实模型配置**跑一次实例化，
  不是纯静态分析能给的。对账表这两个输入仍是推的。
- 探针对 guard 的字段匹配是**基于名字模式**的，存在假阳性（如 `dtype` 命中了非策略的
  局部变量）。未做人工抽样复核，数量级可信、精确值不可信。

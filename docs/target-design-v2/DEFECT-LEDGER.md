# 6. 我认为最容易被漏掉的三条（自评）

## ① **L-005 —— §11.4 与 §6.7 没跟着 §2.5/§6.4 一起改**

它**不是任何一份报告的发现**，而是**修复的残留**：R4-C B-2 论证了"必须给出厂内置开放 `exact`，否则 `G-M2` 第一天就是红的"，正文完整采纳了这条（P2 加了三条限定、§6.4 写了整整一个 bad 框、还加了 `native_exact_ledger`），却**没有改断言这件事的那道门**——§11.4 仍写「`RegisteredOp.self_certainty` 值域**不含** `exact`」，§6.7 步骤4 仍写「`RegisteredOp.self_certainty ∉ {exact}`」。同一格子上还叠了第二处：§11.4 仍写"峰值与 step time **只有区间形态**"，而 §1.4 不变量10 与 `G-X2` 已把 step time 改成 `Sample`。

它容易被漏掉的原因很结构性：**它躲在"已修"这个标签底下**。任何一份按"报告条目 → 是否采纳"来核对的清单，都会在这两条上打勾。只有反过来问"采纳之后，**谁**负责断言它"才会撞见——而 `G-X1` 恰恰是全篇唯一一道"负责断言别的规定还在不在"的门，它现在与两条正文规定同时矛盾。

## ② **L-001 的 `C_eff.hi` 那一半**

六份报告讨论"恒 undetermined"时，路径全部围绕 **`peak.hi`**（`false` 侧）。**没有一份算过 `C_eff` 那一侧的区间算术**：P5 新写的机器选侧规则说"`C_eff` 的减项 ⇒ `upper`"，而 `C_eff.hi = HBM.hi − 减项.lo`——减项取 `upper` 意味着 `.lo` 不可计算 ⇒ **`C_eff.hi` 不可计算** ⇒ §10.2b 表里那句"**会 OOM（`true`）：可判定，只依赖 `peak_lower` 与 `C_eff.hi`**"当场不成立。

两个值同时不可达 ⇒ `G-M2` 恒红 ⇒ 正文刚刚为了防"方案失效"而设的那道元门，在自己的规则下第一天就是红的。而且 §10.2b 只为 `false` 侧写了 `∀ r ∈ S_C : r.hi 可计算`，**从没问过 `C_eff.hi` 需要什么**。

它容易被漏掉，是因为 (a) 它是**两处各自合理的新增修复相乘**的结果（P5 的机器选侧 + §10.2b 的合取式），两处分开看都对；(b) `C_eff` 是减项，方向在减法里翻转一次，而所有报告的直觉都停在加项上；(c) R4-C 6.4 给的那个括号标注（"`upper`（放弃 `C_eff.lo`）"）本身就把方向写反了，正文照抄了它——**错误是从报告继承下来的，因此逐条核对报告永远发现不了**。

## ③ **L-011 —— `CalibKey` 缺 `measured_quantity`**

只有一份报告提出（R3-3 §3.6），埋在六份里最长那一份的第三节第六条，标题还是一个只有编号的门名。它说的是：`workspace_bytes`（显存侧）与同一融合 kernel 的时长（时间侧）可以由**同一次标定跑、同一个域片**产出，而 `CalibKey` 的 schema **没有任何字段区分被标定的是什么物理量** ⇒ §9.2 那道"两侧 `calib` 根无交集"的门在 overlap 全关时**也必然失败** ⇒ 恒假。

而它真正的价值在修法的副产物上：加一个必填闭集字段 `measured_quantity`，同时把 `G-X4` 的「**显存类实测量不得出现在任何门的 oracle 位**」从一句人读的散文变成一个机器可判的谓词。**一个字段修两道门**，其中一道（`G-X4`）是全篇用来隔离"标定 vs 对照"的那道——正文 §0.1、§3.1、§10.2b 序7、§14.3 四处都在引用它，却没有一处说清"显存类"这三个字机器怎么判。
